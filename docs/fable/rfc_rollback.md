# RFC: откат по change_id

Статус: план. В этом раунде ядро откат не выполняет.

## Кто откатывает

Откат делает исполнитель WS2, не супервизор. Ядро хранит факт незакрытой
записи и отдаёт список `change_id`. Исполнитель по этому id возвращает
данные тем способом, который знает только он: версия ноды, снимок или
`restore_action` мягкого удаления.

## Что уже есть в ядре

- Шаг, оборванный на mutating-границе, получает статус `partial` в
  `orch_steps`. Уже записанный `change_id` не стирается.
- Событие `partial_write` с `level=WARN` и списком этих id.
- `Supervisor.list_partial_change_ids(task_id)` и
  `GET /api/orchestrator/chat/{session}/partial-changes?task_id=`.

Повтор того же шага с тем же публичным ключом (в том числе
`idempotency_key`) не вызывает действие второй раз, если строка
`done`, `cancelled` или `partial` уже несёт `change_id`.

## Контракт с исполнителями WS2

Исполнитель позже принимает `change_id` вида `orch-appr-<task_id>-<n>`,
который выдало ядро, и:

- для правки с `reversible=true` возвращает `before` или снимок
  (`snapshot_id` / `archive_ref`);
- для мягкого удаления вызывает свой `restore_action` и снова проходит
  подтверждение, потому что восстановление само destructive;
- чужой или повторный id не применяет (как 404 и 409 у ядра).

Ядро не удаляет строки, не пишет node store и не зовёт git. Пока метода
`rollback(change_id)` у исполнителя нет, список partial id — только
вход для этого будущего вызова.
