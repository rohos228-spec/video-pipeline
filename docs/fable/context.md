## 1. Оркестратор из PR #342 (анализ)
- **Action Layer: 102 действия** в реестре. Каждое действие типизировано, у него свои параметры, уровень риска и стоимость.
- **Planner** строит план через Vibecode (каталог в `app/services/vibecode_catalog.py`, граф в `app/orchestrator/graph/planner.py`).
- **Approvals (HITL):** рискованные и платные действия ждут подтверждения. Auto-approve настраивается.
- **Spend limits:** $200 / $100 / $50 (глобальный / проект / запуск).
- **Kill switch:** немедленно останавливает все действия.
- **Paid-retry guard:** не даёт повторно запускать платную генерацию без явного разрешения.
- **change_control:** журнал изменений с откатом.
- Слабые места:
  - Живого диалога нет: нельзя дописать сообщение посреди задачи.
  - Мультиагентности нет.
  - Автономия ограничена одним планом.
  - Нет маршрутизации fast/strong моделей.
  - Нет RAG по правилам и истории.
  - Нет evals.
  - UI для чата и задач минимальный.
- Оценка: архитектура безопасности сильная, переиспользовать её как основу. Слой диалога и автономии нужно строить сверху.

## 2. Старый чат оркестратора (`app/web/routers/db_browser.py` ~2434)
- Собирает один большой системный промпт из нескольких частей:
  - `_ORCHESTRATOR_SYSTEM`
  - каталог действий
  - карточка проекта (id, slug, title, status, тема)
  - `_pipeline_state_lines`
  - `_checks_context`
  - диагностика
  - фрагменты кода
  - `_settings_context`
  - canvas
  - `_orchestrator_context(graph)`
  - история чата
  - сообщение пользователя
- Режимы: `diagnose_only` (только диагностика) и `fix_bugs`. **В режиме fix_bugs модели разрешены `edit_files` и `run_tests`.** Это прямо противоречит новому требованию: в новом оркестраторе этих инструментов быть не должно, их надо убрать или изолировать.
- Минусы:
  - Один запрос на каждое сообщение, без стриминга.
  - Сообщения посреди задачи не принимаются.
  - Контекст собирается заново целиком, без RAG.

## 4. Правила пользователя (обязательны)
1. Параллельные LLM-батчи с разносом 2–5 с, без лимита одновременных запросов и без долгих ожиданий.
2. `reasoning_effort` high.
3. В проверках никогда не удалять сцены и кадры.
4. Модель — 52pay gpt-5.6-sol.
5. В «Кадрах» склеивать соседние кадры, которые можно объединить (не дробить без нужды).
6. Перед диалогом идёт общий план.
7. Закадр — 200–300 символов на сцену, распределён по кадрам.
8. У оркестратора **нет инструментов редактирования кода и выполнения команд**. Он пользуется только функциями из белого списка. При этом он **обязан уметь создавать любые ноды и отчёты, а также менять любой промпт и параметр ноды**.
9. Перед запуском проверять, что фикс действительно есть в коде студии.
10. Оценки времени давать конкретные.
11. Результаты оформлять HTML-отчётом (редактируемым).
12. Отвечать коротко, по-русски. Не задавать лишних подтверждающих вопросов.

## 5. Продуктовые требования к оркестратору
- Живой чат: стриминг ответов. Сообщения посреди задачи встают в очередь и учитываются: прерывают задачу или корректируют её на следующем шаге.
- Мультиагентность: несколько субагентов под одним супервизором (planner → executor(s) → critic), у задач видны статусы.
- Автономия: многошаговые задачи по проекту с контрольными точками, без лишних вопросов. Безопасность (approvals и лимиты из PR #342) при этом остаётся.
- Полное управление пайплайном из веба: запуск, остановка и resume нод; создание и правка нод и промптов; отчёты; всё это через Action Layer.
- Маршрутизация моделей: простые короткие ответы идут на быструю модель, сложные (планы, ревью) — на сильную (gpt-5.6-sol, high), с запасным вариантом.
- RAG по правилам пользователя, истории проектов и чатов, каталогу нод и промптов.
- Можно переиспользовать open-source (агентные фреймворки, RAG-библиотеки) при условии совместимости с текущим стеком.
- Цикл planner → critic. Программные валидаторы, например длин закадра и отсутствия удалений. Evals на реальных задачах (проект 65 tkach-finalochka как эталон).
- Поэтапный rollout: на каждом этапе контрольные точки и критерии приёмки. Работа делится на 4–8 параллельных потоков, у каждого файлы закреплены только за ним.
- Сохранить текущий дизайн веба (Next.js, `web/src`) и все правки пользователя.
