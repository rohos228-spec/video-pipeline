# Ревью PLAN.md — Фейбл, жёстко и по делу

## 🔴 Критично (блокеры, план в текущем виде не исполним)

**1. PR #342 нигде не вливается в main.** План строит ВСЁ поверх Action Layer из #342, но rollout содержит только merge housepc (R0). Ветка `orchestrator-observe-v1` живёт отдельно, на :8766, со своим DATA_DIR. Когда и как 102 действия, approvals, spend limits и change_control попадают в main — не сказано ни слова. R2 «интеграция Action Layer» молчаливо предполагает, что он уже там. Это дыра размером с фундамент.

**2. Тройной конфликт housepc ↔ main ↔ PR #342 не разобран.** housepc содержит незакоммиченные правки в `app/orchestrator/*` (~30 файлов, прямо указано в контексте). PR #342 — это тоже `app/orchestrator/*`. Этап 0 ребейзит housepc на main «в пользу housepc», а потом кто-то должен влить #342 поверх — конфликты неизбежны, стратегия отсутствует, время не заложено.

**3. Критический путь посчитан неверно.** Заявлено 14 дней: R0(1)+R1(3)+R3(5)+R5(3)+R6(2). Но R3 (executor исполняет план через действия с approval) невозможен без R2 (реестр, 4 дня), а R5 невозможен без R4 (E2 требует «RAG находит ноду», 3 дня). Честный критический путь: R0→R1→R2→R3→R4→R5→R6 = **21 день**, не 14. «14 дней» — самообман в сводной таблице.

**4. Evals гоняют платную генерацию в CI.** E1 содержит `run_node` (risk: high, платно) и заявлено «evals в CI на каждый PR». Копия DATA_DIR не отменяет реальных вызовов 52pay. Это либо сжигание денег на каждый PR, либо evals молча замокают — и тогда E1/E5 (paid-retry) ничего не проверяют. Стратегия мока платных шагов отсутствует полностью.

**5. Пропавшие таблицы БД — ничейные.** `orch_sessions`, `orch_messages`, `orch_events` (п. 3.2) и `orch_reports` (п. 6.1) не входят ни в `orch_schema.sql` (WS3: tasks/steps/checkpoints), ни в `routing/schema.sql` (WS5). Чат WS3? Отчёты WS2? Миграционный процесс для 3+ разрозненных schema-файлов не описан.

## 🟠 Высокий приоритет (пересечения владения и противоречия)

**6. `vibecode_catalog.py` — пересечение WS1/WS2.** Каталог лежит в `app/services/**` (владение WS1), но handler `create_node` (WS2) обязан «регистрировать в каталоге». WS2 пишет в файл WS1. Прямое нарушение собственного правила «без пересечений».

**7. `templates/node_groups/**` не принадлежит никому.** `create_node` и `edit_node_prompt` пишут туда в рантайме, Этап 0 коммитит туда промпт-правила, RAG (WS6) их индексирует. Три потока трогают директорию, которой нет в таблице владения.

**8. Частичное владение `db_browser.py` — не владение.** WS2 владеет «только удалением fix_bugs» в файле на 2434 строки, при этом `diagnose_only` остаётся «легаси до миграции» без владельца, этапа и дедлайна удаления. Кто мигрирует, когда deprecated становится deleted — пусто.

**9. E5 противоречит сам себе и п. 3.3.** «Остановка ≤ 10 с (или до конца текущего LLM-вызова)» — strong-вызов имеет таймаут 300 с с 2 ретраями. Критерий «≤10 с ИЛИ до 15 минут» — это не критерий, это дыра. Раздел рисков добавляет третью версию: «отмена только между шагами для платных действий». Выберите одну семантику и измеряйте её.

**10. Рантайм-записи в git-директории ломают правило 9.** `create_node` создаёт шаблоны в `templates/node_groups/` на работающем сервере → дрейф между репо и рантаймом. Правило 9 («проверять, что фикс есть в коде») и `read_pipeline_code` будут читать состояние, которого нет в main. Механизм синхронизации рантайм-нод с репозиторием не описан.

**11. `read_pipeline_code` без определённого allowlist — ружьё на стене.** «Путь из allowlist» — а список где? Без явного исключения `.env`, конфигов с `PAY52_GPT_API_KEY`, `data/` это канал утечки секретов в контекст LLM. E8 это не проверяет.

**12. `create_report` + contenteditable = XSS.** LLM генерирует HTML, веб его рендерит и даёт редактировать. Ни слова о санитизации (DOMPurify/bleach). Отчёт — редактируемый, значит ещё и пользовательский ввод сохраняется через PUT. Два вектора, ноль митигаций.

**13. Аудит 102 действий — «обязателен», но не запланирован.** «Минус любые exec-подобные, аудит обязателен» — кто, когда, сколько часов, по какому критерию «exec-подобности»? Это основа безопасности, а она висит в воздухе между R0 и R2 без владельца.

## 🟡 Средний приоритет

**14. Правило 4 vs strong-tier.** Правило пользователя: «Модель — 52pay gpt-5.6-sol». План ставит `claude-fable-5` первичной strong-моделью, gpt-5.6-sol — фолбэком. Требования задачи это разрешают, но конфликт с правилом 4 не проговорён явно — нужна строка «правило 4 относится к нодам пайплайна, оркестратор — исключение, подтверждено пользователем». Сейчас это мина.

**15. In-memory состояние vs деплой.** `asyncio.Queue`, SSE-шина, cancel-события — всё внутрипроцессное. Один uvicorn-worker? Несколько? При multi-worker очереди и стримы развалятся. Ограничение деплоя нигде не зафиксировано.

**16. Классификация «<1 с» противоречит собственному SLA.** Fast-tier p95 < 3 с (DoD WS5), но классификатор сообщений обещает <1 с. Одно из двух неправда.

**17. Этап 0 за 6–8 часов — оптимизм.** Коммит 30 файлов логическими кусками, rebase с конфликтами, 4 новых регрессионных теста, полный pytest, Playwright, ревью, merge И бонус-валидатор. Реально 1.5–2 дня, особенно с учётом п. 2 (конфликты в app/orchestrator).

**18. E1 флакует по построению.** Проект 65 УЖЕ содержит 2 фрагмента >300 и 10 <200 (открытая проблема из контекста). Критерий «100% pass vo_length» смешивает качество оркестратора с качеством контента пайплайна — eval будет красным не по вине агента.

**19. Создание узлов противоречит правилу 8.** Правило: «обязан уметь создавать ЛЮБЫЕ ноды». Схема `create_node`: `group: enum <существующие группы>`. Новую группу создать нельзя. Либо расширить схему, либо явно согласовать ограничение.

**20. Spend-интеграция LLM-вызовов оркестратора — «кормит spend limits» без механизма.** Лимиты PR #342 считают стоимость действий. Собственные вызовы planner/critic (strong, high effort — недёшево) учитываются в $50/run или нет? Не определено.
