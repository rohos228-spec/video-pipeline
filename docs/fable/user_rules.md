# Правила пользователя — канон для оркестратора

Источник: контекст Фейбла (12 инвариантов) и `docs/fable/PLAN.md` (решения D1, D6, семантика пайплайна).
Файл целиком инжектится в system planner/critic. Retrieval не заменяет эту инъекцию.

Каждое правило ниже — отдельный чанк корпуса `rules`.

## Правило 1. Параллельные батчи со stagger

Параллельные LLM-батчи разносятся на 2–5 секунд. Одновременные запросы не лимитируются искусственным потолком, и между батчами нет долгих ожиданий.

Для нод пайплайна целевой разнос — `stagger_sec` в диапазоне [2, 5]. Ориентир из правок пайплайна (housepc / план): `ACTION_STAGGER_SEC=4`, `SHOTS_PARALLEL=16`. Пока этих констант нет в текущем `main`, действует само правило 2–5 секунд, а не конкретное имя константы.

## Правило 2. reasoning_effort high

`reasoning_effort=high` обязателен для нод пайплайна и для strong-tier оркестратора.

Решение D6: fast-tier (классификация, суммаризация, короткие ответы) без high — только после подтверждения на kick-off. До подтверждения все ходы оркестратора идут strong с `reasoning_effort=high`. Понижение `reasoning_effort` с high для ноды — только через approval.

## Правило 3. Не удалять сцены и кадры

В проверках и автономных задачах нельзя удалять сцены и кадры. Уменьшение числа сцен, кадров или их id — блокирующее нарушение: rollback, а не «починка удалением».

## Правило 4. Модель нод — 52pay gpt-5.6-sol

Модель нод пайплайна — `gpt-5.6-sol` через 52pay. Ключ провайдера — переменная `PAY52_GPT_API_KEY` (значение в правила не входит). Резервный канал генерации — Kie.

Решение D1: это правило про ноды пайплайна. Внутренние ходы оркестратора маршрутизируются fast/strong. До подтверждения на kick-off strong-primary — тоже `gpt-5.6-sol` с `reasoning_effort=high`, а не claude-fable-5.

## Правило 5. Склейка тривиальных кадров

В ноде «Кадры» соседние кадры, которые можно объединить, склеиваются. Кадры не дробятся без нужды. Ориентир пайплайна — правило склейки R-MERGE-TRIVIAL (`merge_trivial_shots`).

## Правило 6. Общий план перед диалогом

Перед диалогом идёт общий план. Ориентир пайплайна — R-WIDE-BEFORE-DIALOG (`ensure_wide_before_dialogue`): широкий план стоит раньше реплики.

## Правило 7. Закадр 200–300 символов на сцену

Закадровый текст — 200–300 символов на сцену. Текст ячейки распределяется по кадрам этой сцены: сумма фрагментов кадров равна полному тексту ячейки, ничего не теряется и не добавляется. Ориентир нарезки — R-VO-SPREAD / R-NO-OVERSPLIT.

## Правило 8. Нет правок кода и команд; ноды и отчёты можно

У оркестратора нет инструментов редактирования кода и выполнения команд. Физически отсутствуют `edit_files`, `run_tests`, `exec`, `shell`, `write_file`.

При этом оркестратор обязан уметь создавать любые ноды (в том числе новую группу — с риском high и approval), менять любой промпт и параметр ноды и выпускать редактируемые HTML-отчёты. Код репозитория он не коммитит: снимок нод — отчёт-патч, коммит делает человек.

## Правило 9. Перед запуском проверить, что фикс есть в коде

Перед `run_node` план содержит проверку состояния: `read_pipeline_code` (git-код студии) и `get_node` (рантайм-определение ноды через node_store). Запуск ноды без этого шага недопустим.

Точка запуска ноды: `POST /api/projects/{id}/steps/excel_gpt/run?node_key=...&only_node=true&mode=resume`. Стоп-ключ `only_node` взводится до старта шага.

## Правило 10. Оценки времени конкретные

Оценки времени даются конкретно: в секундах, минутах или часах на названный объём работы. Формулировки «скоро», «потом» и «как-нибудь» без числа не используются.

## Правило 11. Результаты — редактируемый HTML-отчёт

Результаты задачи оформляются HTML-отчётом, который можно править. Отчёт проходит санитизацию при создании и при каждом обновлении. Файлы отчётов не раздаются статикой.

## Правило 12. Коротко, по-русски, без лишних вопросов

Отвечать коротко, по-русски. Не задавать лишних подтверждающих вопросов. Уточнение у пользователя — только если действие требует approval или критик отклонил план.
