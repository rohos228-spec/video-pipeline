## Какие ноды покрыты

- **Включено (ограниченное самовосстановление):** `excel_gpt`, `plan`, `script`. Повтор или смена профиля, затем проверка
  результата; обязательные точки подтверждения человеком (HITL) оркестратор никогда не подтверждает сам.
- **Намеренно выключено, с причинами:** `split` и `image_prompts` (при ошибке JSON нечего восстанавливать / нативный
  верификатор блокирует выполнение), медиа-ноды — только человек, потому что повтор может оплатить генерацию дважды
  (`docs/MEDIA_NODES_READINESS.md`).

## Что проверено живыми запросами, а что нет

- Подтверждено живьём: восстановление `excel_gpt` (1 запрос решения + 1 запрос повтора, около $0.0095), агентный цикл.
- Не подтверждено живьём: восстановление `plan` и `script`. Прогон дошёл до запроса решения и остановился:
  провайдер вернул `402 Credits insufficient` (баланс Kie отрицательный). Оркестратор корректно остановился и передал
  случай человеку. Механика этих нод проверена прогоном без платных вызовов. Повтор — после пополнения баланса.
- Ограничение метода: сбой воркера в живых прогонах моделировался локальным бракованным ответом, потому что реальную
  модель нельзя заставить вернуть битый JSON по требованию. Смысловое качество результата система не оценивает
  (`semantic_quality_verified = false`): проверяются структура и применение данных.

## Как это работает (по шагам цикла)

1. **Наблюдение.** Каждый вызов модели и каждый запуск ноды пишут события (какая нода, какая попытка, что вернула модель,
   сколько токенов и денег). Это единый журнал состояния.
2. **Диагностика.** Отказ получает класс: битый JSON, отказ контракта, нехватка кредитов, таймаут с неопределённым
   запросом и т.д. От класса зависит, что можно делать дальше.
3. **Нативные повторы.** Сначала ноду повторяет сам конвейер (3 цикла). Оркестратор не вмешивается, пока они не исчерпаны.
4. **Решение.** Только после этого модель-«решатель» выбирает из разрешённого списка действий: подождать, повторить так же,
   повторить с другим профилем, позвать человека, завершить. Свободно менять код или промпты она не может.
5. **Исполнение.** Один ограниченный повтор на ноду. Профиль (например, `production-json-repair-v1`) — заранее описанный набор
   параметров и подсказки, не произвольная правка.
6. **Проверка.** Результат проверяется по структуре и применению данных. Обязательные подтверждения человека (HITL)
   оркестратор не одобряет никогда.
7. **Итог.** Либо нода `done`/ждёт человека, либо эскалация `REQUIRES_HUMAN_INTERVENTION` с причиной. Лимиты: не более
   3 шагов решения, потолок запросов и стоимости на прогон.

## Для каких нод что сделано

| Нода | Оркестратор | Чем проверено |
|---|---|---|
| `excel_gpt` | Включён: повтор / смена профиля | Живой прогон (≈$0.0095), тесты |
| `plan` | Включён: повтор / смена профиля | Прогон без платных вызовов; живой остановил баланс Kie (402) |
| `script` | Включён: повтор / смена профиля | То же |
| `split` | Выключен: при битом JSON нечего восстанавливать | Анализ кода + тесты |
| `image_prompts` | Выключен: нативный верификатор блокирует выполнение | Анализ кода + тесты |
| `images`, `videos`, `hero`, `items` | Только человек: повтор может оплатить генерацию дважды | Анализ кода + 14 тестов (`docs/MEDIA_NODES_READINESS.md`) |
| `audio`, `music`, `sfx_gen` | Только человек: нет идемпотентности, провайдер мог уже списать деньги | То же |
| `assemble`, `publish` | Только человек: финальный результат / необратимая публикация | То же |

## Что не сделано и почему

- Этап 4 в полном объёме (свободная правка промптов, перенос нод на NodeSpec): решение владельца не расширять права автоматики.
- Живое восстановление `plan`/`script`: нужен положительный баланс Kie.
- Живые прогоны медиа-нод: повтор платной генерации небезопасен без идентификатора задачи; требования описаны в
  `docs/MEDIA_NODES_READINESS.md`.
- Доставка на GitHub: по решению владельца всё хранится локально.
