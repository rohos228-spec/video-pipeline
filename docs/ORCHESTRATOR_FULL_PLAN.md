# План доработки оркестратора до всех нод

Основа: 5 аудитов кода и 4 исследования интернета (2026-10-02), полные отчёты с file:line и URL лежат в `docs/research/`.
Метки: [Ф] факт из кода/источника, [О] мнение, [Г] гипотеза, требующая проверки. Всё непроверенное помечено.

## 0. Что показали исследования (главное)

**Находки, которые меняют приоритеты:**
1. **Платная ошибка есть уже в самом конвейере, не только в оркестраторе.** [Ф] Рестарт процесса во время `generating_*` заново ставит в очередь кадры без файла и повторно платит; таймаут при опросе Kie (`RETRY_BURN`) создаёт новую задачу при живой оплаченной; идентификатор задачи Kie живёт в локальной переменной (`kie_http.py:387`). Чужой GitHub-кейс подтверждает двойную оплату при таймауте + повторной отправке. Пока это не закрыто, включать автоповторы на медиа нельзя.
2. **Платные вызовы звука невидимы.** [Ф] ElevenLabs/Suno/SFX не попадают в журнал и учёт расходов (наблюдение навешано только на GPT); их таймауты диагностика считает `contract_rejected`, а не «неопределённый запрос».
3. **Ядро ненадёжно в краевых случаях.** [Ф, по чтению кода] Деградация наблюдателя необратима, одна ошибка помечает все выполнения; глобальная квота журнала 32 МиБ без очистки заблокирует всё; `commit_uncertainty` только в памяти; рубильник расходов `check_api_allowed` нигде не вызывается; нет суточного/денежного потолка; нет сторожа зависших запросов.
4. **Безопасность доступа.** [Ф] По умолчанию авторизация выключена, CORS `*`, часть мутаций и все чтения журнала без проверки; `error_message` уходит в облачный трекер без редактирования; старый чат-оркестратор умеет править `app/`/`prompts/` и делать `git push`, что обходит принцип «серьёзное — только с разработчиком».
5. **`enrich_1…5` отдельно включать не нужно.** [Ф] Живые ноды — это `excel_gpt`, повтор у неё уже есть. Старый тип `enrich_N` в графе даёт «не поддерживается»; решение: мигрировать графы, а не добавлять алиас. Прежний аудит считал их отдельными типами — поправлено.
6. **Стоимость видео занижена в прежней оценке.** [Ф] Дефолт проекта 1080p: Seedance 2.5 = около $2.85 за отправку, худший случай около $12.2 за клип (было $7.1).
7. **`reasoning`-модели: возможная причина `missing payload`.** [Г] `max_output_tokens` включает токены рассуждений, ответ может прийти пустым/обрезанным. Лечится бюджетом токенов и `reasoning.effort`, а не починкой JSON. Проверить на нашем Kie.
8. **Починка обрезанного JSON опасна.** [Ф источников] Библиотеки превращают обрезанный список операций в валидный, но неполный. Усечение — отдельный класс, без автопочинки.
9. **Апстрим `housepc` не закоммитил `nii67_card.py` и UI «НИИ 67».** [Ф] В `make_script.py` стоит защита, Studio взяла наши версии двух файлов.

## 1. Принципы (из исследований, обязательны для всех этапов)

- Детерминированный автомат с закрытым списком действий; LLM только диагностирует и предлагает. Права ограничиваются механически (нет прав записи в код), а не текстом промпта.
- Идемпотентность на логическую операцию: свой `job_id` до вызова провайдера, `provider_task_id` сразу после ответа; исходы `fail` / `timeout` / `submit_unknown` — только `fail` разрешает повторную отправку. После таймаута: «возобновить опрос, не отправлять заново».
- Повторы на одном уровне стека, с классификацией, jitter и общим бюджетом; учитывать повторы SDK провайдера.
- Защита от петель на трёх уровнях: подпись действия, счётчик по проблеме (не сбрасывается при смене подхода), потолки на запуск.
- Бюджет вне контроля агента: ключ провайдера, проект, запуск, отдельный бюджет восстановления, проверка перед каждой платной попыткой, остановка по 402.
- Результат проверяется объективными признаками артефакта (ffprobe, схема, инварианты, diff с входом), не самоотчётом LLM. Проверка смысла — только после и только с человеком/калибровкой.
- Подтверждения трёхъярусные (само / уведомить / одобрить), по истечении времени — запрет; публикацию и финал одобряет человек.
- Каждая нода считается закрытой только при выполнении пяти условий: (1) описана данными, (2) журнал, (3) диагностика, (4) безопасное действие или явный запрет с причиной и тестом, (5) тесты без платных вызовов + один живой прогон под потолком.

## 2. Фазы

### Фаза A. Надёжность ядра (блокер для всего остального)
Задачи (ID из `docs/research/code_core_review.md`, разд. 8):
- A1. Деградация наблюдателя обратима и изолирована по выполнению; ошибка цикла не метит все execution (T1).
- A2. Очистка/ротация журнала и тел, квота по проекту, удалить O(N) `glob` на запись (T2).
- A3. `commit_uncertainty` в БД, не в памяти (T3).
- A4. Сторож (watchdog): зависшие запросы и выполнения, три таймера, карантин «ядовитого» запуска; вынести вызов модели решений из общего цикла (T16).
- A5. Аварийный стоп всех выполнений (kill switch).
- A6. Реальные миграции схемы вместо `create_all` (T8): нужны для фаз D–F.
Критерий: тесты на рестарт, на сбой в середине записи, на переполнение квоты; сухой прогон с убитым процессом.

### Фаза B. Безопасность и расходы
- B1. Авторизация включена по умолчанию, привязка к localhost, проверка Origin вместо CORS `*`, `AuthDep` на мутации и чтение журнала (T6).
- B2. Редактирование (`redact`) `error_message` и тел перед записью в любой трекер; облачная отправка за флагом (T9, T4).
- B3. Закрыть правку кода и `git push` из старого чата-оркестратора (T7). **Решение владельца**: отключить или оставить за подтверждением разработчика.
- B4. Рубильник расходов реально подключить (`check_api_allowed` вызывается до платных вызовов); глобальный/суточный/денежный потолок; учёт стоимости медиа и звука; отдельный бюджет восстановления (T4, T5, L1–L6).
- B5. Журнал расходов (ledger) и сверка с балансом провайдера; остановка по 402/433.
Критерий: тесты, что при исчерпанном потолке ни один платный вызов не уходит; негативные тесты авторизации.

### Фаза C. Декларативные ноды (NodeSpec) и покрытие в UI
- C1. `NodeSpec` несёт поля способности (профиль, нативный JSON-повтор, продолжение, летучие вложения), верификатор, контракт, исполнитель; реестр читается кодом (T10).
- C2. Убрать цепочки `if node_type…` в `observation.py:790-850` и `decision_v1.py:257-357` (T11); приёмка по контракту, не по типу (T14).
- C3. Разделить `input_revision`/`graph_version` на структурную и конфигурационную часть (T12, T13) — условие для фазы G.
- C4. Мигрировать 12 записей способностей, по одной, отдельный коммит с тестами; тест «добавь ноду» (conformance).
- C5. Панель «Покрытие нод» в Studio: журнал / диагностика / восстановление / причина запрета по каждому типу (проект дизайна — `code_core_review.md` разд. 7).
- C6. Миграция графов с `enrich_N` на `excel_gpt`.
Критерий: новая нода подключается данными без правки ядра; панель показывает честные статусы.

### Фаза D. Текстовые ноды
- D1. Живое подтверждение `plan` и `script` (после пополнения баланса Kie): потолок $0.10 на прогон. Заодно измерить гипотезу про токены рассуждений (пробный запрос с разным `reasoning.effort`).
- D2. Класс «усечение»: `finish_reason`/`incomplete_details`, завершающий маркер и счётчик операций в схеме; автопочинки нет.
- D3. `sfx_plan` — первая новая нода с `retry_same`. Требуются правки: `payload_required` в `parse_result`, привязка к `request_id`, `data_applied`, собственный контракт для `read_contract`, сброс чекпоинта `ai_jobs["sfx_plan"]` перед повтором, потолок числа событий. Сухой + живой прогон ≤ $0.10.
- D4. `animation_prompts`: сначала только наблюдение; повтор условно (ворота G3 запрещают после первой записи батча).
- D5. `sd_agent`/`sd_assemble`: только наблюдение (идентичность ноды неоднозначна, чекпоинты вне `input_revision`). `scene_design` (старая) — только человек. `hero` — только наблюдение; `items` — только возобновление по task id (см. F5).
Критерий: охранные тесты, сухие прогоны, по одному живому на включённый тип.

### Фаза E. Кадры: `split` и `image_prompts`
- E1. `split`: вариант A — метка «чем получены кадры» (ответ модели / блоки / локальная разбивка) и неблокирующий инцидент деградации. Затем решение владельца между B (проверка до записи в БД, защита от «ответ-отказ записан как кадры») и C (один внутренний повтор до локальной разбивки). Полный `retry_same` (D) — только после защиты от раннего выхода `split_completed`.
- E2. `image_prompts`: оркестратор читает, пересчитывает проверку только чтением и объясняет причину удержания; снятие hold остаётся за человеком. Включение повтора только при выполнении девяти условий из `code_split_imgpr.md` (табл. 2.3).
- E3. Поле `rule` в `node_error` и факт `rule_diary`, чтобы оркестратор видел дневник и правила R-* группы `script_frames_qc` (апстрим).
Критерий: сухие прогоны; живые под потолком $0.10.

### Фаза F. Медиа: картинки, видео, герои, предметы
Требует фазы A, B (учёт расходов) и фикса платных дефектов конвейера.
- F1. Журнал платных попыток: `reserved` до POST → `submitted` + `provider_task_id` → `succeeded` + URL → `downloaded`; неоднозначный исход = стоп. Типизированные исключения `KieSubmitUnknownError`, `KieTaskPending`.
- F2. Исправить в самом конвейере: рестарт во время `generating_*` не ставит заново кадры с живой задачей; таймаут опроса не создаёт новую задачу; потолок числа регенераций (`vision_check_loop` до 20 раундов, `mark_frames_for_video_regen`).
- F3. Скачивать результат сразу (сроки хранения у Kie противоречивы: 20 мин – 14 дней).
- F4. Против настоящего Kie для `media_jobs`: авторизация в `json_request`, загрузка референсов, снять loopback-ограничение. Вебхук добавить поверх опроса (идемпотентный обработчик).
- F5. Действие `resume_poll` для `images`, затем `videos` (сначала `managed=True`), `hero`, `items`. Сделано для `videos`, `items`, `music`: действие `media.resume_poll` (`local_safe`: платных запросов не создаёт, проверяется по журналу) и билет восстановления надзора только на возобновление; `images` управляется синтетическим путём, `hero` не допущен (`nondeterministic_paid_request`). Решено сухим прогоном: надзорный повтор `assemble` и готовых файлов `audio`/`sfx_gen` не допущен (`docs/NODE_COVERAGE.md`, раздел «Локальные медиа-ноды»). Снятие блокировки неизвестного исхода человеком: `media.list_unknown_outcomes` (чтение) и `media.release_unknown` (`destructive`, разовое подтверждение, причина, провайдер и ключ, запись в журнал до и после, предупреждение о втором списании).
- F6. Живой прогон по шагам с потолками. Картинки ≈ $0.06 за submit. Видео 1080p Seedance 2.5 ≈ $2.85 за submit — только по отдельному разрешению, лучше 720p/дешёвая модель для проверки механики.
Критерий: 15 стаб-тестов (`code_media_image_video.md`), тест «краш после submit до записи taskId» не создаёт второй платной задачи.

### Фаза G. Звук, сборка, публикация
- G1. Наблюдение и учёт расходов для ElevenLabs/Suno/SFX; типизация таймаутов (`ElevenLabsApiError`, `KieHttpError` → «неопределённый запрос»).
- G2. `audio`/`music`: диагностика + эскалация; позже «только возобновить» (когда файл уже на диске или известен taskId); платный повтор TTS не разрешать (27 POST на сценарий, до 54 с прокси — сначала сократить нативные).
- G3. `sfx_gen`: повтор по отдельным событиям ≤ 1 на событие, без молчаливого `local_synth` при ошибке провайдера.
- G4. `assemble`: атомарная запись (временный файл + переименование), `verify_artifact(kind="assembly")`, проверка длительности/дорожек/чёрных кадров/тишины/громкости; после этого один повтор. Барьер `approve_final` не снимается при `auto_mode`/`HITL_AUTO_APPROVE` без проверки.
- G5. `publish`: только человек навсегда (необратимо, правила платформ требуют ручного подтверждения и маркировки синтетики); read-only preview; исправить `ok=True` после `sleep(8)` на фактический результат.

### Фаза H. Этап 4 плана (смена параметров/промптов) — только при разрешении владельца
Не свободная правка. Цикл: предложение (`proposed`) → прогон на золотом наборе → одобрение человеком → версионное применение (CAS-указатель) → проверка → откат одним кликом. Тиры T0–T3 (параметры / выбор варианта промпта / текст промпта / логика ноды), для T3 — только разработчик. Старт с параметров и выбора варианта, не свободного текста. Подробности: `code_core_review.md` разд. 4 и `web_llm_structured_and_tuning.md`.
