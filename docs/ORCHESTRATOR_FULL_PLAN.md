# План: довести оркестратор до всех нод

Отправная точка (2026-10-02): полный цикл включён для 3 из 24 типов нод (`excel_gpt`, `plan`, `script`); журнал и диагностика
для 6 (`+ split`, `image_prompts`, `images`); остальные — только человек. Источник: `docs/ORCHESTRATOR_AUDIT_5_DAYS.md`.

Правило для каждой ноды: нода считается закрытой, только если выполнены все пять условий.
1. Описана в `node_capabilities` (данные, а не ветки по строке типа).
2. Журнал: старт, запрос, ответ, разбор, применение, проверка.
3. Диагностика: у каждого отказа есть класс и допустимые действия.
4. Восстановление включено только там, где повтор не может повредить данные или оплатить дважды; иначе явно «только человек» с причиной в данных и тестом.
5. Проверено: тесты без платных вызовов + один живой прогон с потолком расходов (если нода тратит деньги).

## Этап 2. Нода `split` и `image_prompts` (правки самих нод)
- `split`: определить, что считать отказом. Сейчас при битом JSON нода штатно строит разбивку закадра локально, `parse_result` с `payload_required=false`, инцидента нет. Нужно решение: фиксировать «локальная разбивка вместо ответа модели» как деградацию с классом инцидента и разрешить один повтор.
- `image_prompts`: нативный верификатор после первой неудачи ставит hold на выполнение, и нативные повторы не исчерпываются. Нужно добавить в диагностику класс «held by native verifier» и допустимое действие «снять hold + один повтор» (под защитой: только на контрактных ошибках, не на `contract_rejected` по смыслу).
- Критерий: сухой прогон по схеме `e2e_text_nodes_recovery.py` + живой прогон с потолком $0.10 каждая.

## Этап 4. Медиа-ноды (самое дорогое и рискованное)
Принцип: повтор платной генерации запрещён, пока у запроса нет сохранённого идентификатора задачи провайдера.
1. Сохранять `taskId` провайдера в журнале сразу после отправки (сейчас живёт в локальной переменной, `kie_http.py:387`).
2. Разрешить единственное безопасное действие: «возобновить опрос по сохранённому taskId» (не новая отправка).
3. Включить управляемый маршрут `media_jobs` не только на синтетическом транспорте (сейчас loopback, `media_jobs.py:155`).
4. Порядок: `images` → `hero`/`items` → `videos` → `audio`/`sfx_gen`/`music`.
5. На каждую: сухой прогон на синтетическом провайдере, затем живой прогон с жёстким потолком (оценки в `docs/MEDIA_NODES_READINESS.md`: суммарно около $2.1, без Seedance 2.5; Seedance 2.5 — отдельное согласование, ~$1.58 за 5-секундный клип).
- `videos`: сначала `managed=True` (сейчас False), только потом восстановление.
- `audio`/`sfx_gen`: у ElevenLabs нет ключа идемпотентности и клиент уже сам повторяет 3 раза; восстановление включать не будем, максимум — диагностика и эскалация. Явное решение зафиксировать в данных.
