# Локальные денежные лимиты надзорного слоя

Модуль `app/services/spend_guard.py`. Работает без сети: облачный рубильник `api_tracker_hook` не используется.

## Журнал
Таблица `spend_ledger` (основная БД, только добавление; UPDATE и DELETE запрещены триггерами). Поля: день (UTC), вид
(`reserve` резерв, `settle` разница факта и резерва, `actual` нативный вызов, `event`), провайдер, проект, запуск
(execution id или `plan:<id>`), источник, USD, кредиты. Создаётся при первом обращении (`ensure_schema`).

## Потолки (0 = без ограничения)
Решение заказчика: денежного лимита нет, важно, чтобы не было бесконечного «брак -> перезапуск». Поэтому суммы ниже это
высокие предохранители от ошибки и утечки (обычный ролик в них не упирается), а от зацикливания защищают счётчики
перегенераций (раздел «Потолок перегенераций»). Все значения настраиваются; `0` выключает потолок.

| Настройка | По умолчанию | Область |
|---|---|---|
| `SPEND_DAILY_CAP_USD` | 200 | все проекты, сутки UTC |
| `SPEND_PROJECT_CAP_USD` | 100 | проект, за всё время |
| `SPEND_RUN_CAP_USD` | 50 | один запуск или план |
| `ACTION_LAYER_SESSION_CAP_CREDITS` | 10000 (около $50) | один план слоя действий |
| `SPEND_AUTO_KILL_ON_402` | true | авто-стоп при нехватке кредитов |

Окно запуска (`run`) берётся из явного `run_id`, а если шов его не передал, из контекста корреляции (`request_context`):
та же колонка `run_id`, под которой строка запишется в журнал. Поэтому потолок запуска действует и на нативных швах (C-8).

Резерв и проверка трёх потолков выполняются одним атомарным INSERT ... SELECT: две одновременные заявки не
пройдут вместе, если помещается только одна. Отказ: `SpendCapExceeded` с кодом `spend_cap_run`, `spend_cap_project` или
`spend_cap_daily`, суммой потрачено и потолком. Чтение никогда не блокируется (`check_allowed(..., read_only=True)`).

## Где подключено
- `ActionSupervisor.charge_request`: в той же транзакции, что счётчик запросов, до отправки. Оценка текстового запроса
  0.05 USD (измеренные вызовы 0.00005-0.008), платная отправка медиа 0.30 USD, статус, загрузка и upload бесплатны.
- Слой действий, `budget.reserve`: после проверки кредитного потолка плана; кредиты переводятся в USD по
  `kie_catalog.CREDIT_USD` (0.005). `budget.settle` дописывает разницу.
- Планировщик: резерв 0.05 USD перед POST; отказ превращается в `PlannerRefused` с тем же кодом.
- Факт: `observation._track_api_cost` (успешные вызовы с реальным ключом) закрывает резерв либо пишет нативный вызов.
  Платный нативный вызов проходит шлюз `spend_guard.paid_gate` ДО отправки: аварийный рубильник, свободное место на
  диске и три потолка (суммы журнала плюс открытые резервы плюс оценка этого вызова). Шлюз отклоняет вызов с
  `PaidCallBlocked` (запрос не отправляется); если сама проверка не сработала, вызов тоже отклоняется (fail-closed). Это
  касается и запасного клиента Kling (`kie_kling._create_task` под `paid_seam`), у которого свой HTTP-клиент.
  Не отклоняются только вызовы, которые не платные (статус, скачивание, загрузка).

## Авто-стоп по 402
Ошибка с кодом `gpt_credits` или `media_credits` (HTTP 402) при `SPEND_AUTO_KILL_ON_402=true` включает существующий
аварийный стоп (`kill_switch`, основание `credits_exhausted`, источник `spend_guard`, запись в историю и ActionRecord
каждого управляемого запуска). Стоп касается только надзорной работы: запросы супервизора, решения, восстановление, слой
действий, новый тик управляемого проекта. Неуправляемые нативные проекты не останавливаются. Снимается оператором.

## Интерфейс
`GET /api/projects/{id}/observations/spend`: суммы за сегодня, по проекту и запуску против потолков. Панель
оркестратора показывает их в блоке после аварийного стопа.

## Ограничения
- Суммы по нативным вызовам считаются по тарифной таблице трекера (калибровка только для текста), медиа нативного
  конвейера пишется оценкой (см. раздел ниже).
- Оценки консервативны; неизвестный факт оставляет резерв.
- Резерв слоя действий, который не закрылся фактом (таймаут без подтверждённой остановки, итог шага неизвестен, шаг
  без проекта), не висит молча: через `ACTION_LAYER_RESERVE_STALE_S` (3600 с) после конца шага он получает метку
  `reserve_unresolved` в журнале слоя (одна на шаг) и виден в `GET /api/action-layer/reserves`. Сумма остаётся в потолках.
  Снять её может только оператор, сверив кабинет провайдера: `POST /api/action-layer/reserves/release` с причиной
  (отрицательная сверка в `spend_ledger` и `action_layer_spend`, событие `reserve_released`).
- Ошибка 402 на нативных медиа-путях Kie, Outsee, ElevenLabs включает авто-стоп через `media_spend`; браузерный Outsee
  по-прежнему не включает авто-стоп по 402 (страница не отдаёт код), но его повторный клик после неизвестного исхода
  заблокирован (`outsee_guard.run_browser`, см. раздел о возобновлении).

## Потолок перегенераций по деньгам (`app/services/regen_budget.py`)
Счётчики попыток (`REGEN_MAX_PER_FRAME`, `REGEN_MAX_PER_RUN`) не знают цену раунда: 12 кадров стоят дороже одного.

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `REGEN_MAX_USD_PER_RUN` | 25.0 | оценка USD всех перегенераций одного шага (0 = без ограничения) |
| `REGEN_ESTIMATE_USD_PER_ITEM` | 0 | оценка одной перегенерации кадра или героя; 0 = `MEDIA_SUBMIT_ESTIMATE_USD` (0.30) |

Раунд стоит `число кадров x оценка`; vision-проверка добавляет ещё `DEFAULT_REQUEST_ESTIMATE_USD` (0.05). Раунд, который
вывел бы шаг за потолок, не ставится: проект на паузе с `auto_paused_reason`, диагностика показывает инцидент
`human_review`. Первый раунд шага деньгами не блокируется. Это отдельный счётчик от `SPEND_*_CAP_USD` (те считают
фактические записи журнала и режут отправку запроса); здесь только оценка, чтобы остановить цикл раньше.

## Нативные платные медиа-вызовы (модуль `app/services/media_spend.py`)
Запись только учётная: вызов провайдера, его повторы и результат не меняются, ошибка записи не доходит до вызывающего
кода, запись идёт фоновой задачей (локальная вставка, без ожидания в запросе). Строки `spend_ledger` с источником
`media_native`, проект берётся из `_cost_project`. Запись выключена без реального ключа провайдера (пустой или
`synthetic*`) и внутри pytest (флаг `media_spend.TEST_FORCE` только для тестов).

| Провайдер | Точка подключения | Оценка |
|---|---|---|
| Kie (jobs/veo/suno/runway) | `kie_http.create_task` (стоимость и task id), `poll_task` (статус, число опросов одной строкой с 0 USD) | `kie_catalog.estimate_credits` x `CREDIT_USD`; модель без цены: строка запроса с `cost_unknown=true` |
| Kling-запасной клиент | `generate_kie_video`, ветка без каталожной модели (одна строка на вызов); шлюз перед отправкой в `kie_kling._create_task` | каталог `kling-2-6-i2v` / `-t2v`, иначе `cost_unknown=true` |
| Outsee API | обёртка вокруг `outsee_http.generate_image/generate_video` в `outsee_retry` | тарифа в коде нет: всегда `cost_unknown=true` |
| ElevenLabs TTS | каждый POST в `elevenlabs_api` (повторы и повтор без прокси считаются отдельно) | символы x `ELEVENLABS_USD_PER_CHAR` (0.0003, **не откалибровано**); при заголовке `character-cost` пишется строка `settle` |
| ElevenLabs sound effects | `sfx_gen._elevenlabs_sfx` | секунды x `ELEVENLABS_SFX_USD_PER_SEC` (0.012, **не откалибровано**) |

Неопределённый исход (таймаут, обрыв, ответ без task id) пишется по оценке: запрос мог быть принят. Однозначный отказ
(4xx, в том числе 402) пишется с 0 USD.

HTTP 402 или исчерпание кредитов на этих путях вызывает `spend_guard.engage_on_credit_error` (при
`SPEND_AUTO_KILL_ON_402=true`, только надзорный стоп) и пишет строку `event` с источником `media_402`. Нативная работа
не останавливается.

`provider_task_ledger` (основная БД, только добавление, UPDATE и DELETE запрещены триггерами): проект, ключ кадра или
клипа (имя файла без суффикса), task id, провайдер, модель, событие, статус, оценка. Состояние задачи это её последняя
строка (`submitted`, затем `pending` или `succeeded` или `failed`). Повторные отправки и опросы не меняются, таблица
нужна как durable-основа для будущего «возобновить опрос». `GET /api/projects/{id}/observations/provider-tasks`.

Диагностика: таймаут или обрыв после отправки в клиентах ElevenLabs и Kie поднимается как `ElevenLabsUncertainError` /
`KieUncertainError` (подклассы прежних ошибок) и даёт `uncertain_request`.

Ограничения: тариф Outsee и Kling-запасного клиента (task id) не учтены, task id запасного Kling-клиента теперь тоже пишется в журнал (см. раздел о возобновлении), не
пишется; `character-cost` не проверялся на реальном ответе; константы ElevenLabs оценочные.

## Возобновление, а не повтор (`app/services/media_resume.py`)
Нативные Kie-картинки и Kie-видео (включая запасной Kling-клиент) больше не отправляют второй `createTask`, пока
первая задача может быть жива или оплачена. Источник истины: `provider_task_ledger`. Ключ: проект, ключ кадра или клипа
(`frame_012`, `clip_012_s2`), модель, хэш запроса (модель и поля без ссылок на референсы). Окно: `MEDIA_RESUME_WINDOW_S`
(по умолчанию 3600, 0 = выключено). Работает только для вызовов с явным `project_id` и реальным ключом.

Строки журнала сверх прежних: `intent` (статус `submit_unknown`, пишется и ждётся ДО POST), `intent_done`
(`bound` или `rejected`), `bound` (task id получен), `downloaded` (результат на диске, конечное состояние).

| Ситуация | Что происходит |
|---|---|
| Рестарт или повторный проход шага, задача жива (`submitted`, `pending`) или `succeeded` без `downloaded` | опрос того же task id, скачивание результата, нового `createTask` нет |
| Таймаут, 5xx или обрыв сети при опросе | опрос продолжается с паузой до конца прежнего бюджета, затем `KieTaskPending`; лестница не сжигает попытку и не отправляет заново |
| Результат готов, скачать не удалось (3 попытки) | `KieTaskPending` (`kind=download`), статус остаётся `succeeded`, следующий вход только скачивает |
| `createTask`: таймаут чтения, обрыв после отправки, ответ без task id, шлюз 504 | `KieSubmitUnknownError`, intent остаётся неразрешённым, повторный submit по тому же запросу запрещён до конца окна |
| `createTask`: ошибка соединения до отправки (`ConnectError`, `ConnectTimeout`, `PoolTimeout`) | исключение как раньше, intent снимается, бесплатный повтор лестницы работает |
| Явный отказ провайдера (4xx, 402, 5xx кроме 504), `state=fail` по известной задаче | поведение лестницы прежнее: новая попытка допустима |

`KieSubmitUnknownError` и `KieTaskPending` (`kie_http.py`, подклассы `KieUncertainError`) в `video_error_policy`
превращаются в действие `HOLD_UNKNOWN` (`is_no_resubmit`), в обеих лестницах `outsee_retry` пробрасываются без
retry, rewrite и fallback. У Kie нет списка задач, поэтому исход потерянного submit подтвердить автоматически нельзя.
Действие человека: сверить задачи и баланс в кабинете Kie; списания не было: `media_resume.release_unknown(project_id,
key)` (или подождать окно); списание было: задача оплачена, результат взять в кабинете.

Одноразовая сверка при старте (`media_resume.reconcile_on_startup`, вызов в `app/main.py` до стартового отката
статусов): для проектов в `generating_images` и `generating_videos` по каждой открытой задаче один запрос статуса;
готовые результаты скачиваются в `scenes/` или `videos/`, неудачные помечаются, живые остаются шагу (он подхватит их
через `begin`). Новых submit нет. Бюджет 90 секунд, ошибки не останавливают запуск.

Task id кадра пишется в `Artifact.meta.provider_task_id` (картинки) и в журнал по ключу кадра.

Outsee через браузер (`OutseeBot`) теперь тоже под записью намерения: клик, после которого нет ни результата, ни отказа
страницы, считается отправкой с неизвестным исходом, новый клик по кадру запрещён в окне `MEDIA_RESUME_WINDOW_S`.

Что остаётся небезопасным: Outsee (API и CDP) не отдаёт клиенту task id, возобновлять нечего (повторы после известного
отказа лестница оплачивает заново, после неизвестного исхода её останавливает защита выше); потерянный `createTask` без task id решает только человек; при сбое БД запись журнала пропускается (вызов
провайдера не блокируется); окно считается от первого submit, задача старше окна считается мёртвой; цикл
`finalize_or_retry` и `vision_check_loop` по-прежнему могут запускать новые платные регенерации (они удаляют файл, а
`downloaded` конечный); мёртвая ветка Kie-картинок в `outsee_retry` (`backend == "kie"` внутри `if use_outsee_api`) не
тронута; типы `KieSubmitUnknownError` и `KieTaskPending` надо добавить в `UNCERTAIN_ERROR_TYPES` диагностики (сейчас
сравнение по точному имени типа).
