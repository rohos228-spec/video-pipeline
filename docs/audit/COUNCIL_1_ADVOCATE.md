## 1. Почему именно такой объём

### 1.1. Что значит «готовый регистратор» (измеримое определение)

Регистратор готов, когда выполнены ВСЕ шесть свойств; каждое проверяется данными, а не заявлением:

1. **Полнота действий.** Любое мутирующее обращение (кнопка Studio, слой действий, скрипт, надзор) оставляет строку «кто, что, когда, над каким проектом, чем кончилось». Сегодня оставляют только вызовы через слой и управляемые запуски: около 150 мутирующих эндпоинтов роутеров (58 в `project_ops.py`) не оставляют ничего (AUDIT_3 §2.2, AUDIT_2 §3.9).
2. **Полнота трат.** Каждый платный вызов даёт строку с проектом, запуском и ФАКТИЧЕСКОЙ суммой, суммы сходятся с балансом провайдера. Сегодня: четыре несвязанных хранилища, факт слоя всегда `null`, Outsee всегда «$0, неизвестна», потеря строки молчалива (`except: pass`), три платных шва вообще без записи (AUDIT_3 §2.1, §3, §5; AUDIT_2 §3.1; AUDIT_1 §0.7).
3. **Полнота ошибок.** Каждый сбой типизирован, читается по-русски и приводит к исходу (повтор, эскалация человеку, остановка). Сегодня 29 из 49 видов событий показываются сырым именем; `api_error`/`contract_rejected`/`uncertain_request` не имеют автоматического исхода (AUDIT_3 §4, AUDIT_1 §1).
4. **Каждая нода наблюдается и проверяется всегда.** Сегодня журнал включается только вручную (`observation.py:1293`), проверка результата у `plan/script/split/image_prompts` только в управляемом режиме, у `images` её нет вовсе (AUDIT_1 §0.3, §0.5, §3.8).
5. **Доказано вживую, а не моками.** Сегодня живое доказательство есть только у `excel_gpt` (и то со смоделированным сбоем) и у трёх «швов» (картинка, TTS, SFX). `plan`/`script` не пройдены (Kie 402), медиа-ноды, сборка, слой действий на платных операциях, публикация не прогонялись ни разу (AUDIT_1 §0.6, AUDIT_2 §0.4, AUDIT_5 §1.3).
6. **Публикация с подтверждением человека и доказательством.** Сегодня успех не детектируется ни на одной из 5 платформ (все `unconfirmed`), при выключенном флаге проект ложно становится `published`, ретрай после клика даёт дубль (AUDIT_4 §3, §4).

Любое меньшее определение («только тесты», «только наблюдение», «MVP публикации») оставляет хотя бы одно из этих свойств недоказанным, то есть «регистратор» остаётся витриной. Заказчик прямо исключил заглушки, MVP и тесты-без-живого, поэтому план покрывает все шесть.

### 1.2. Почему нельзя сузить

- **Без фазы 0** (диск, CSRF, секреты, бэкап) регистратор небезопасно запускать: диск уже был забит на 100% (7,9 ГБ мусора `pid-*`), любая открытая вкладка браузера способна пройти `from-text → approve → run` (AUDIT_5 §0.1-0.2), журнал может нести ключи (AUDIT_3 §7).
- **Без фазы 1** регистратор пуст по определению: именно она закрывает свойства 1-3. Это сердце заказа, а не «хорошо бы».
- **Без фазы 2** журнал есть, но нод не покрывает (свойство 4).
- **Без фазы 3** оркестратор не умеет действовать на боевых провайдерах: управляемая медиа-ветка работает только на loopback с синтетическим ключом (`media_jobs.py:158,208-212`, `actions_v1.py:286`), Decision выключен по умолчанию (`decision_config.py:188-198`). То есть «всё автоматизировано» сегодня неверно по построению.
- **Без фазы 4** «всё записывается» ложно: около 60% контролов Studio слою неизвестны (AUDIT_2 §1.2), а платные шаги конвейера недоступны слою (`node.run_step` только `excel_gpt`).
- **Без фазы 5** нет публикации; заказчик её требует явно, а текущий код в боевом пути даёт ложный успех.
- **Без фазы 6** остаются все «доказано сухим прогоном»: именно на живых шлюзах нашлись настоящие дефекты (SFX 404, ключ `/v1/sound-effects`, Outsee без task id, `items` шлёт Kie-слаги в Outsee).
- **Фаза 7** (тесты, документы, поставка) нужна, потому что документы противоречат коду (14/9/1 против 11/12/1; 268 против 21/29 падений), а 29 красных тестов делают любой «зелёный» отчёт недоверчивым.

### 1.3. Принципы плана

1. Сначала «видеть» (фазы 0-2), потом «действовать» (3-5), потом «доказывать вживую» (6): так каждый живой платный прогон записывается и сверяется полностью.
2. Живые прогоны идут лестницей по цене: центы, затем доллары; перед каждым ⏸ потолок утверждает владелец; до/после сверка баланса.
3. Платная повторная отправка по-прежнему только у нативного слоя или человека; надзор возобновляет и сверяет, но не платит дважды (принцип идемпотентности из ORCHESTRATOR_FULL_PLAN §1 сохраняется).
4. Публикацию агент не выполняет сам НИКОГДА: он готовит, человек подтверждает, исполняет детерминированный код (требование «с подтверждением»; в реестре `publish` остаётся hard-disabled для управляемого режима).
5. Ничего не называется «сделано» без строки в колонке «Готово когда»; сухие и живые критерии разделены.

### 1.4. Чего план осознанно НЕ обещает

- Смысловое качество результатов (текст, картинки, видео): сегодня `semantic_quality_verified=false` везде. План даёт объективные проверки (файл, ffprobe, схема, инварианты) и человеческую выборочную оценку (шаг 83), но не «ИИ-судью».
- Работу селекторов платформ без данных и тестовых аккаунтов заказчика: шаги 62-69 физически невозможны до получения данных (список в §5).
- Порт в WebVideoPipeline заказчика (Postgres, арендаторы, Alembic) входит как отдельный шаг 87, ЗАКАЗЧИК/менеджер; он зависит от решения ветки, которого в репозитории нет.
