## 1. Выбор аккаунта / профиля

- Один профиль на всё. `morelogin_browser(profile_id=None)` берёт `settings.morelogin_profile_id` (app/bots/morelogin.py:84), настройка единственная строка `MORELOGIN_PROFILE_ID` (app/settings.py:242). Если пусто, ошибка (morelogin.py:85-86).
- `publish_everywhere` открывает профиль один раз и в нём последовательно проходит все 5 платформ (publishers.py:214-225). Докстринг прямо говорит: "через один MoreLogin-профиль" (publishers.py:1). Следствие: все 5 аккаунтов должны быть залогинены в одном профиле.
- Конфигурации по платформе, по аккаунту, по проекту нет. В модели Project нет поля профиля или аккаунта; шаг публикации не читает ничего, кроме `project.topic/slug/meta` (steps/publish.py:78-81). Мульти-канальность (несколько каналов одного бренда, разные проекты в разные аккаунты) не поддержана.
- `BROWSER_CDP_URL` (settings.py:39) к публикации не относится: используется только в chrome_cdp.py / browser.py (генерация, Outsee) и monitor (grep по `browser_cdp_url`). Публикация CDP-Chrome напрямую не использует, только через MoreLogin. Запасного пути "обычный Chrome" для публикации нет.
- Порт MoreLogin API 40000 захардкожен (morelogin.py:44, параметр host по умолчанию), не настраивается. Эндпоинты старта подбираются из 3 кандидатов (morelogin.py:28-37), формат ответа версионно-зависим (комментарий morelogin.py:10-12); на реальном MoreLogin не верифицировано. Для запуска отправляется только `profileId`; авторизации API (app id / secret, как в новых версиях MoreLogin) нет.
- В `finally` профиль останавливается (morelogin.py:95-103), `browser.close()` на CDP-подключении к MoreLogin может закрыть браузер клиента, пока оператор что-то делает руками (риск, не проверен).

## 2. Поток публикации (на платформу)

`Publisher.publish` (publishers.py:81-114): открыть upload_url (или переиспользовать вкладку того же хоста, :50-62) -> найти `input[type=file]` и `set_input_files` (:85-88) -> найти поле подписи и `fill(caption)` (:91-97) -> найти кнопку Post/Publish и клик (:100-103) -> `_confirm`.

Слабые места:
- Загрузка: после `set_input_files` нет ожидания окончания аплоада и обработки видео. Сразу ищется поле подписи, затем кнопка с таймаутом 60 с, и в `_first_visible` проверяется только `count() > 0`, а не видимость и не enabled (publishers.py:74; имя метода врёт). Кнопка Post в TikTok/YT неактивна/disabled, пока идёт загрузка: клик по disabled-кнопке даст timeout/ошибку либо ложный "клик прошёл".
- Подпись: ошибка заполнения лишь логируется как warning (:96-97), пост уйдёт БЕЗ подписи, и считается успешным шагом.
- Подпись = `project.topic or slug` [:2200] (steps/publish.py:78), одинакова для всех платформ: нет хэштегов, нет лимитов по платформам (TikTok 2200 ок, но YT title 100 символов, IG 2200 и 30 хэштегов, VK и Likee свои), нет заголовка YT (title), нет описания отдельно, нет языка/аудитории (YT "made for kids" обязательное поле: без ответа Publish недоступен), нет обложки.
- Расписание (schedule) НЕ реализовано нигде: публикация только "сейчас" (grep по schedule в publishers.py пуст). Лимит постов/день не соблюдается, нет пауз между постами кроме 3 с между платформами (:224).
- YouTube: `upload_url = https://studio.youtube.com/channel/UC/videos/upload` (:152): "UC" это заглушка, не реальный channel id, на живом Studio, скорее всего, редирект/ошибка; flow YT Studio многошаговый (Details -> Elements -> Checks -> Visibility -> Publish), одной кнопкой `#done-button` его не пройти без шагов "Next" и выбора Public. Инстаграм: upload_url = главная страница (:168), file input на ней не появляется без клика Create -> Reel (комментарий :166-167 признаёт); селектор Share тоже на втором шаге после Next. Для TikTok/VK/Likee вероятно ближе к рабочему, но тоже не калибровано.
- Селекторы: модуль сам заявляет "кандидаты, не верифицированы на живом UI" (publishers.py:7-8). Есть recon-режим (`python -m app.bots.publishers recon <platform>`, :228-269), но результатов калибровки в репозитории нет.

## 3. Детекция успеха

- В базовом классе `success_selectors = []`, `success_url_markers = []` (publishers.py:43-44). Ни один из 5 подклассов их не переопределяет (TikTok :136-147, YT :150-161, IG :164-171, VK :174-182, Likee :185-189). Т.е. ПУСТЫЕ У ВСЕХ 5 ПЛАТФОРМ.
- При пустых списках `_confirm` ждёт 8 с и возвращает False (:118-120) -> всегда `status="unconfirmed"`, `ok=False`. То есть автопубликация в текущем виде ни разу не вернёт "confirmed" (тест test_phase_g_assemble_publish.py:242-246 фиксирует это; "confirmed" проверен только на тестовом подклассе с выдуманным `div.done`, :250-258).
- Даже при подтверждении записываемый `url=page.url` (publishers.py:106) это URL страницы загрузки/студии, а не URL опубликованного поста. Реальной ссылки на пост нет ни в одном исходе. Success proof (скриншот, ссылка, id поста) не сохраняется.
- Успех по URL-маркеру опасен: `m in page.url` срабатывает сразу, если маркер входит в upload-URL (напр. "studio" и т.п.), поэтому маркеры надо выбирать осторожно.

| Модерация / отказ платформы / лимит постов | Нет чтения сообщений об ошибках на странице. После клика: `unconfirmed`. Пост может быть отклонён, а система об этом не узнает. |
| Невалидное видео / формат | Не проверяется до клика; ошибку платформы никто не читает. |

Клик и последующая ошибка не различаются: статус "точка невозврата пройдена" не фиксируется. |

Если процесс упал после публикации в TikTok, но до записи meta, информация о посте потеряна, на повторе все 5 платформ опубликуются заново. Нет записи "попытка начата" до клика (write-ahead). |
| Падение MoreLogin на платформе №3 | Exception в `publish` ловится по платформе, цикл идёт дальше; но сбой старта профиля (`morelogin_browser`) вне try (publishers.py:214) поднимется наверх; шаг упадёт целиком, ничего не записано, предыдущие платформы не вызывались (это безопасно). |
| Одновременный запуск двух воркеров на проект | Нет блокировки/lease на публикацию (кроме статуса проекта); гонка = двойной пост. Не проверено, как pipeline.py:183 защищён от параллельного запуска; идемпотентного ключа нет. |

Идемпотентность: частичная. Что есть: пропуск платформ из `published_platforms` и `publish_unconfirmed` (steps/publish.py:79-87), тест на это (test_phase_g...:262-299), если `unconfirmed` на всех платформах, ретрай не идёт (:90-93). Что отсутствует: пропуск `failed`-после-клика, запись намерения до клика, ключ идемпотентности на (проект, платформа, sha256 файла), сверка с реальной лентой аккаунта (проверить, нет ли уже такого поста) перед повтором, привязка записи к конкретному артефакту (если проект пересобран и final_video новый, `published_platforms` в meta всё равно блокирует публикацию новой версии, и наоборот не отличает версии).
Так как успех (confirmed) не достижим при пустых маркерах, фактически ВСЕ платформы попадают в `publish_unconfirmed`, `published_count` никогда не доходит до 5 (steps/publish.py:122-133), проект навсегда остаётся в `publishing`, пока человек вручную не очистит meta. Комментарий в :128 говорит "остаёмся в assembled", но статус остаётся publishing (расхождение документации и кода). Ключ "unconfirmed" не имеет пути выхода: нет UI/действия "подтвердить вручную" в просмотренном коде (искал только в app/orchestrator/steps/publish.py и по grep `publish_unconfirmed`; не искал в UI отдельно, помечаю как "не найдено").

## 5. Как записываются результаты

- Только в `project.meta["published_platforms"]` (platform -> url) и `["publish_unconfirmed"]` (steps/publish.py:17-18, 97-106) плюс сообщение в Telegram владельцу (:120). Отдельной таблицы публикаций нет: нет времени, id поста, файла/артефакта (uuid, sha256), аккаунта/профиля, числа попыток, скриншота, ошибки. Эти поля нужны для аудита и для идемпотентности.
- URL = страница загрузки (см. п.3), не ссылка на пост.

## 6. Гейтинг (human-only)

- Переход assembled -> publishing идёт через HITL `approve_final` (auto_advance.py:199-202). То есть человек подтверждает финальное видео.
- Глобальный выключатель: `SOCIAL_PUBLISH_ENABLED=false` по умолчанию (settings.py:243); при выключенном шаг ничего не публикует, но ПОМЕЧАЕТ проект `published` (steps/publish.py:61-65): это ложный "опубликовано" (статус published без единого поста), метрики/батчи (services/batches.py:378, 595) посчитают как done. Это надо исправить отдельным статусом (напр. `publish_skipped`).
- Управляемый (агентский) режим публикации запрещён жёстко: при `get_permission(project.id)` или scope.mode == "managed" шаг бросает MediaPolicyError (steps/publish.py:57-58). В реестре возможностей: `publish` = `_MEDIA_HUMAN_ONLY`, класс `external_side_effect_not_money`, "managed publication is hard-disabled and a retry could publish twice" (services/node_capabilities.py:445-448). То есть оркестратор-наблюдатель публикацию не запускает и не ретраит; ретрай только человеческий.
- `preview_publication` (steps/publish.py:21-49): read-only, браузер не открывает, проверяет наличие и валидность final-артефакта, показывает список платформ и признак already_recorded; `send_allowed: False`. Подпись в превью только длиной (:30).

Противоречие, которое надо снять: путь `pipeline.py:183-184` вызывает `publish.run` для статуса publishing в обычном (не managed) режиме, т.е. человек/штатный воркер публикует реально; managed блок отдельно. Корректно как "human-only", но "человек" = просто approve_final + включённый флаг, без второго подтверждения именно публикации (список платформ и подпись не показываются перед публикацией).

## 7. Как наблюдает оркестратор

- Наблюдатель видит узел publish как human-only (node_capabilities.py:445), результат фактов не верифицирует (нет независимой проверки поста). `preview_publication` даёт dry-run.
- Единственный след: Telegram-сообщение и meta. Проверки "пост реально живой" нет.

4. Состояние логинов в профилях, частота слёта сессий, наличие 2FA/капчи.
5. Правила и лимиты платформ для конкретных аккаунтов (дневные лимиты, новые аккаунты, shadowban при автоматизации, ToS: автоматизация web-UI у TikTok/IG нарушает ToS; официальные API (TikTok Content Posting API, YouTube Data API, Instagram Graph API, VK API) более надёжны и легальны, стоит обсудить).

7. Региональные ограничения (TikTok/Instagram в РФ, нужен ли прокси профиля).
