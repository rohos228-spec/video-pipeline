## 0. Подготовка (обязательно, иначе тестируешь старый код)

1. На ПК: `git pull` (ветка из `.env` `ORCHESTRATOR_GIT_BRANCH`, обычно `main`).
2. `stop-backend.cmd` → `STUDIO.cmd` → пункт [1]. Python-процесс подхватывает
   код только через рестарт — проверь бейдж версии слева внизу Studio:
   номер должен вырасти, `/api/studio-version` без `ui_stale=true`.
3. Открой http://127.0.0.1:8765, вкладку «Логи» держи открытой рядом.
4. Тестовые проекты: **#8** (`image_prompts_ready`) и **#13** (`frames_ready`).
   **#61 НЕ трогать** (`videos_ready`, прод). **#14** — отдельный пункт 9.
5. Не запускать ноды audio/music (вне контура; harness их не чинит).

Легенда результата: PASS = ожидаемое поведение; FAIL = расхождение →
сразу собери пакет ошибки (пункт 10) и зафиксируй шаг/проект/время.

## 10. Сбор ошибок (при любом FAIL)

1. Кнопка «Баг» в топбаре → «Сохранить и скачать» (пакет с логами).
2. `data/backend-*.log` — хвост за время FAIL.
3. «База» проекта → «Проверки» → JSON (или `GET /api/projects/{id}/harness/status`).
4. `project.meta.step_failure` — код ошибки (`apply_ops_unknown_uuid`, …),
   счётчики, `sleep_until`.
5. `data/videos/<slug>/ops/events.jsonl` — события harness/apply по шагам.
6. Скриншот UI + точное время + номер проекта + нода.

## 11. Известные дефекты UI (не репортить как новые — из аудита)

- P0: «Отправить на главный ПК» и polling активных передач → 404 (роутов
  нет, кнопки Fleet не трогать в этом прогоне).
- P1: «Сброс шага», удаление ноды/связей, корзины в «Монтаже», «Очистить»
  хранилища — без confirm; кликать только осознанно.
- P1: write-кнопки в «Базе» молчат при ошибке API — если кнопка «не
  сработала», смотри консоль/сеть в devtools.

## 12. Критерий «зелёного» прогона

Все PASS в пп. 1–9; ни одного необъяснённого FAIL; ни одного
`step_failure` с новым кодом; папка videos/ без сирот; «База» и
«Монтаж» показывают только актуальные данные после любого wipe.
