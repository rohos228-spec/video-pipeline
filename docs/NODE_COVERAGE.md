# Покрытие нод оркестратором: что проверяется, что запрещено и почему

Источник правды — данные в коде, не этот файл: `CapabilitySpec` каждой ноды (`app/services/node_capabilities.py`,
`app/orchestrator/node_spec.py`). Панель «Покрытие нод» берёт их из `GET /api/projects/{id}/observations/node-coverage`
(`app/services/node_coverage.py`), таблица ниже — то же самое словами. Проверка: `tests/observe_v1/test_node_coverage.py`.

## Три уровня

- **Под управлением (managed).** Принят исполнитель и проверка результата: оркестратор может запустить ноду, проверить
  итог по журналу и независимому перечитыванию данных. Автоповтор есть не у всех (см. столбец «Повтор»).
  Исключение: `videos`, `items`, `music` «под управлением только для восстановления» (`recovery_only`): надзор
  возобновляет уже известную задачу провайдера и проверяет результат, но саму ноду никогда не запускает, не
  перезапускает и новой платной отправки не делает.
- **Под наблюдением (observed).** Автодействий нет. Есть проверка результата, перехватчик или описание контракта для чтения;
  попытки пишутся в журнал. Решает человек.
- **Только человек (human_only).** Кроме общего журнала попыток, у оркестратора ничего нет по этой ноде.

Уровень вычисляется из данных (`coverage_level`), его нельзя объявить словами: «под управлением» требует принятого
исполнителя (`acceptance`), «под наблюдением» требует проверку/перехватчик/описание, иначе нода «только человек».

## Правило «добавил ноду»

Тест `test_every_registered_node_type_has_a_capability_spec` падает, если тип ноды есть в реестре конвейера
(`WORK_NODES` + виртуальный `excel_gpt`), а `CapabilitySpec` для него не зарегистрирован. Для новой ноды достаточно
записи «только наблюдение» с кодом причины запрета (`forbidden_code`): так она сразу видна в панели честно.
Остальные тесты не дают записи соврать: уровень должен подтверждаться данными, запрет — кодом из справочника
`KNOWN_FORBIDDEN_CODES` и фразой не короче десяти слов, повтор — лимитом 1 и перечнем ограничений.

## Таблица по нодам (24 типа: 23 рабочих + виртуальный `excel_gpt`)

Для `videos`, `items`, `music` столбец «Повтор» значит другое, чем у текстовых нод: билет восстановления (один на ноду за запуск, как
у текстовых) разрешает ровно одно действие, `media_recovery.assess`-допущенное возобновление по уже известному task id. Подробности
и ограничения: раздел «Допуск медиа: возобновление вместо повтора» ниже.

Повтор означает один `retry_same` на ноду за запуск, с общими защитами: нативные повторы шага исчерпаны, ни одной
применённой записи в упавшей попытке, вход не изменился, первый запрос повтора совпадает с исходным, бюджет, нет
`user_stop`, человеческое утверждение (HITL) не снимается.

медиа-ноды `videos`, `items`, `music` только возобновляют известную задачу провайдера), под наблюдением 12, только человек 1
(`publish`, навсегда). Нормальная работа ноды по-прежнему идёт нативным путём; оркестратор смотрит, проверяет, в пяти случаях один
раз повторяет упавшую попытку и в трёх медиа-случаях один раз докачивает уже оплаченный результат.

## Что изменено в D3–D5 (журнал, проверки, повтор)

- `sfx_plan`: разбор пишет `payload_required` и `payload_present` (только для ответа модели, не для чекпоинта), поэтому
  нераспознанный ответ типизируется как `invalid_json`, а JSON без `events` как `missing_payload`; нарушение правил
  таймлайна остаётся `contract_rejected`. Нативная `plan_sfx.run` перед своим коммитом ставит в тот же транзакционный
  коммит факт `data_applied` (без него проверка повтора невозможна, подставного факта нет). Перед повтором невалидный
  чекпоинт сбрасывается только внутри попытки восстановления (иначе повтор проиграл бы его без запроса к модели).
  В управляемом запуске план, не подтверждённый независимым перечитыванием, удерживает запуск (по образцу `split`);
  при нативном сбое ничего не удерживается.
- `animation_prompts`: `parse_result` получил `payload_required`/`payload_present`; повтор допустим, пока не было ни одного
  `apply_input`/`data_applied`/`apply_error` (общая защита от частичного применения).
- `animation_prompts` (вторая очередь): при сбое провайдера нативный путь по-прежнему добивает кадры локальным шаблоном или
  пропускает остаток `shot_02` без ошибки, но теперь пишет факт `animation_degraded` (причина `local_fallback` или
  `shot2_skipped`, номера кадров, класс причины). Диагностика делает из него инцидент `animation_degraded`: предупреждение,
  не блокирует, статус `human_review`, в `RECOVERY_INCIDENTS` его нет. Полный сухой проход по настоящему исполнителю с лентой
  картинок: `tests/observe_v1/test_animation_prompts_dry_run.py` (подменён только запрос к модели).
- `sd_agent`, `sd_assemble`, `scene_design` (вторая очередь): проверка результата и типизация сбоев для всех агентов веера и
  для сборки. Контракт среза выведен из кода (`agents.parse_agent_slice`, `cells.slice_to_cells`), а не из промптов:
  `skeleton` и `action` — непустой `scenes` с `id_scene` (у `skeleton` ещё `кадры`), `characters` — непустой список с id `cNN`,
  `world` — список `locations` с id `locNN` (пустой допустим), `camera` — непустой `shot_plan` с цитатой. Ответ без JSON даёт
  `invalid_json`, JSON без нужного списка или с ошибкой агента — `missing_payload`, срез или ячейки против контракта —
  `contract_rejected`. Журнал привязывается к узлу попытки: агент проверяется, когда попытка идёт на узле этого агента.
  Проваленная проверка результата даёт инцидент `contract_rejected` с классом сбоя. Повтор не включён ни для одного агента
  (причины в таблице выше); сухой проход по настоящему шагу: `tests/observe_v1/test_scene_agents_dry_run.py`.
- `enrich_N`: данные покрытия и код причины запрета; поведение не менялось. Для `hero`, `items`, `music` см. раздел про медиа-ветку ниже.
- Данные покрытия не входят в ревизию входа для восстановления: правка текста причины не обнуляет билеты.

## Медиа-ветка: контракт, проверка результата, восстановление

Нормальная работа этих нод по-прежнему идёт нативным путём. Новое — перечитывание результата, охрана от повторной оплаты и
чтение состояния «что можно безопасно возобновить». «Под управлением» стали только `videos`, `items`, `music` и только в смысле
возобновления (см. раздел «Допуск медиа»); `hero`, `audio`, `sfx_gen`, `assemble` остались под наблюдением.

**Что появилось в коде**

- Проверка результата `app/services/media_verification.py`. После шага отдельная сессия перечитывает то, что шаг оставил:
  файл существует, не пустой, лежит внутри папки проекта, картинка декодируется, у видео и звука `ffprobe` видит нужные
  дорожки и длительность. Рядом читается журнал платных задач (`provider_task_ledger`): у задачи Kie есть устойчивый task id,
  у Outsee его нет, и это записывается. В журнал событий пишутся `node_output` и `node_result_verification`; диагностика
  показывает инцидент `media_failure` (не прошло проверку: блокирующий; не подтверждено, например нет `ffprobe`:
  предупреждение) и `uncertain_request` для прошлого платного запроса без известного исхода. Проверка только наблюдает:
  запуск не удерживает и не роняет. Качество картинки, клипа или голоса не оценивается.
- Режим «только возобновление» `media_spend.resume_only()`. Внутри него отказывают все места, которые отправили бы новый
  платный запрос: Kie `createTask`, Kling, Outsee (API и браузер), ElevenLabs (озвучка и звуки). Ошибка `ResumeOnlyBlocked`
  приходит до отправки, запись о намерении не создаётся, лестницы видео и картинок останавливаются, а не жгут попытку.
- Оценка и возобновление `app/services/media_recovery.py`. `assess` читает состояние и отвечает одним из вердиктов:
  `denied` (исход прошлого запроса неизвестен или единственный повтор потрачен), `resume_poll` (открытая задача Kie),
  `resume_local` (готовый файл уже на диске), `retry_same` (разрешён один раз, только если все прежние платные задачи ключа
  достоверно упали), `nothing_to_do`. `resume_poll` спрашивает Kie про уже известную задачу, скачивает готовое и не создаёт
  ни одного нового запроса. Профили по нодам лежат в `RECOVERY_PROFILES`.
- Нативные правки, которые это замыкают: `hero`, `items` и `music` теперь передают номер проекта в платный вызов (раньше не
  передавали, и журнал возобновления для них не работал); ключи `hero_*`, `predmetN` и `music` включены в охрану
  «возобновить, а не отправлять заново»; запуск при старте процесса теперь смотрит и проекты в `generating_hero`,
  `generating_items`, `generating_music`; `music` при незавершённой задаче берёт сохранённый промт и не вызывает GPT заново.
  `sfx_gen`: по событию не больше одного повторного платного вызова, только если откат был после ответа провайдера. `assemble`:
  одна повторная попытка при сбое сборки или проверки итога.

**По нодам: что проверено без сети и что ещё не доказано**

| Нода | Проверено (сухие прогоны, подменён только платный провайдер) | Не доказано, нужен живой прогон |
|---|---|---|
| `videos` | Перезапуск посреди генерации: тот же task id опрашивается и скачивается, новых запросов 0. Опрос не уложился: задача остаётся той же. Неизвестный исход у Kie и Outsee даёт `denied` и ничего не опрашивает. Внутри `resume_only` лестница без известной задачи останавливается с нулём отправок. Повтор допускается один раз и только после достоверного сбоя (сервисом; надзор платную отправку не делает). Билет надзора (`test_media_dry_run_videos.py`): наблюдение, диагностика, решение, один билет, возобновление тем же task id, независимая проверка файла (ffprobe), в журнале ни одного нового task id. | Реальные ответы Kie на опрос и скачивание, сроки хранения результата, реальные клипы Seedance/Kling для `ffprobe`. ## Допуск медиа: возобновление вместо повтора

Текстовую ноду восстанавливают перезапуском (один `retry_same`). Платную медиа-ноду так восстанавливать нельзя: перезапуск может
снова отправить запрос и заплатить дважды, а рабочий процесс под управляемым запуском идёт через другой транспорт (`media_jobs`,
только синтетический профиль), а не через журнал задач, по которому доказан вердикт. Поэтому допуск устроен уже и не перезапускает ноду.

**Как это работает** (`app/services/media_admission.py`, ветка в `recover_node`, `decision_v1`, `diagnosis`)

1. Инцидент: `media_failure` или `uncertain_request` ноды `videos`, `items`, `music` (диагностика помечает такие инциденты признаком
   `media`). Прочие типы и прочие ноды получают типизированный отказ `node_not_admitted`.
2. Решает `media_recovery.assess`: допускаются только `resume_poll` (открытая задача Kie) и `resume_local` (готовый файл уже на диске).
   `retry_same` (все прежние задачи достоверно упали) НЕ выполняется: отказ `retry_same_not_admitted`, повтор платной отправки делает
   нативный слой или человек. `denied` (неизвестный исход отправки, исчерпанный повтор, журнал отключён или недоступен) даёт отказ
   `verdict_denied` с кодом вердикта; `nothing_to_do` даёт отказ `nothing_to_do`. Оценка читается ДО выдачи билета: отказ не оставляет следа.
3. Операция выполняется в процессе надзора внутри `media_spend.resume_only()`: любое место, которое отправило бы новый платный запрос
   (Kie createTask, Kling, Outsee, ElevenLabs), отказывает до отправки. Рабочий процесс ноды не запускается.
4. Проверка из независимых фактов: файлы результата перечитываются (существует, ffprobe видит дорожку и длительность, картинка
   декодируется), журнал `provider_task_ledger` сверяется до и после (ни одного нового task id и ни одного намерения отправки),
   оценка после возобновления не должна оставаться `resume_poll`. Иначе билет `human_review` и исполнение удерживается.
5. Общие защиты те же, что у текстовых нод: аварийный стоп до выдачи билета, область и выданное право исполнения, бюджет запросов
   надзора, один билет на ноду и запуск (UNIQUE в БД) и владелец решения, проверка ревизии входа, совпадение графа, `user_stop`,
   нативные повторы исчерпаны, нода в состоянии `failed`. Билет не повторяется после перезапуска процесса: застрявший билет
   удерживается для человека (`settle_interrupted`).

**Ревизия входа для медиа** (`revisions.compute_input_revision`) считается по данным ПЛАТНОГО ЗАПРОСА (промты анимации кадров,
описания предметов, текст темы и закадра, настройки и код ноды), а не по прогрессу, который записывает сама упавшая попытка (статус
кадра, счётчик неудач, метка «в работе»). Основа записывается при старте попытки и в наблюдаемом запуске без управляемой области
(`observe_attempt`), поэтому билет можно выдать после того, как оператор включил исполнение для уже упавшей ноды.

**Что надзор не делает и почему**

- Не запускает и не перезапускает ноду (`recovery_only`): `require_managed_capability` отказывает управляемому запуску и рабочей
  попытке этих нод. После проверенного возобновления ноду продолжает человек обычным запуском, но пока исполнение включено, рабочая
  попытка такой ноды под управлением удерживается: сначала исполнение закрывается существующим `close` (нужны: ни одна нода не
  выполняется, билет не ждёт проверки).
- Не повторяет платную отправку по провалу (см. п. 2), не возобновляет Outsee (нет task id), не трогает `hero` (промт строится GPT
  заново при каждом запуске), `audio` и `sfx_gen` (нет ключа идемпотентности), `assemble` (нет платной задачи; повтор требует
  перезапуска рабочего процесса, проверка которого для не-модельных нод не доказана), `publish` (необратимо).
- Под управляемым запуском боевой платный Kie закрыт политикой (`media_jobs.assert_entry`: только синтетический профиль), поэтому
  ни управляемый запуск, ни перезапуск надзором этих нод в бою невозможны по конструкции; возобновление идёт в процессе надзора.

**Действия слоя действий** (`app/services/action_layer/builtin_media_recovery.py`, эндпоинты `app/web/routers/media_recovery.py`)

- `media.get_recovery_assessment` (уровень «чтение»): вердикт, ключи с task id, допуск надзора и код отказа. Ничего не меняет.
- `media.resume_poll` (уровень `local_safe`, без подтверждения): тот же сервис возобновления. Уровень выбран потому, что новых платных
  запросов действие отправить не может (режим «только возобновление») и это проверяется по журналу задач; провайдеру уходит только
  запрос состояния оплаченной задачи и скачивание результата. Отказ в предпросмотре: идёт шаг проекта, аварийный стоп, нет задачи,
  которую допустимо докачать. Только `videos`, `items`, `music` (остальные не входят в перечень допустимых значений схемы).
- `media.list_unknown_outcomes` (уровень «чтение»): ключи проекта, у которых прошлая платная отправка (Kie или Outsee) без известного
  исхода и поэтому блокирует повтор; у каждого провайдер, возраст и окно блокировки (`MEDIA_RESUME_WINDOW_S`). Ничего не меняет.
- `media.release_unknown` (уровень `destructive`, разовое серверное подтверждение, привязанное к хэшу плана): решение человека снять
  блокировку после сверки кабинета провайдера. Оно СНОВА ОТКРЫВАЕТ платную повторную отправку, второе списание возможно; текст
  предпросмотра на русском говорит об этом прямо. Параметры: проект, ключ (`clip_005`, `frame_012`, `predmet3`, `music`), провайдер
  (`kie` или `outsee`) и письменная причина (не короче 10 символов). Снимается блокировка только названного провайдера по одному
  ключу: если ключ заблокирован и Kie, и Outsee, вторая блокировка остаётся (`outsee_guard.release_unknown` для Outsee, для Kie то же
  по намерениям Kie). Журнал действий (`action_layer_history`, только дописывается) получает запись до и после: причина, ключ, провайдер,
  кто подтвердил (оператор израсходованного подтверждения, а не параметр), номер плана, сколько намерений снято. Отказ в предпросмотре:
  идёт шаг проекта, по ключу у этого провайдера нет блокировки в окне; эндпоинт отказывает и при аварийном стопе. Сервис:
  `app/services/media_unknown.py`; эндпоинты `GET .../media-recovery/unknown-outcomes`, `POST .../media-recovery/release-unknown`.
  Само действие ничего не отправляет. Тесты: `tests/test_media_unknown_release.py`.

## Локальные медиа-ноды: допуск повтора надзором решён сухим прогоном (`assemble`, `audio`, `sfx_gen`)

Вопрос: можно ли для этих нод выдать надзорный билет на один повтор (для `audio` и `sfx_gen` только на уже готовые файлы, никогда на
новый платный запрос). Ответ: пока нельзя, ноды остаются под наблюдением. Сухой прогон
`tests/observe_v1/test_media_dry_run_local_nodes.py` (настоящий `assemble._assemble_body`, настоящий `verify_artifact` с ffprobe на
реальных файлах, настоящие журнал, диагностика, надзор решений и защиты `recover_node`; подменён только монтажный движок, отправка в
Telegram и хук массовой фабрики, провайдера в этом пути нет) разделяет доказанное и недостающее.

Доказано безопасным:

- один повтор внутри ноды: только при сбое сборки (ошибка `ffmpeg`) или проваленной проверке итога, не при ошибке входа и не при отмене;
- запись атомарная: прежний итог переживает каждую неудачную попытку, остатки `.part.mp4` не лежат, `verify_artifact` читает НОВЫЙ файл до подмены;
- `approve_final` один на пару проект и sha256, остаётся `pending` для человека; ничто в пути сборки его не одобряет;
- платный запрос недостижим: прогон внутри `media_spend.resume_only()` с заглушками всех платных мест не обращается ни к одному; разбор
  импортов модулей сборки не находит Kie, ElevenLabs, Outsee, GPT; `recover_before_assemble` не вызывает ни восстановление героя из Outsee,
  ни озвучку.

Недостаёт (поэтому допуск не выдан; каждый пункт закреплён тестом, который упадёт, когда это появится):

1. Повтор сборки идёт только рабочим процессом (нужны Bot, сессия проекта, ffmpeg). Медиа-ветка `recover_node` рабочий процесс не
   запускает (возобновляет задачу провайдера в процессе надзора), а ветка рабочего процесса построена вокруг модельного запроса:
   факты `model_start`, инцидент `invalid_json` / `missing_payload`, хэш первого запроса. Проверка в `reconcile` требует
   `data_applied` и `parse_result`; сборка не пишет ни того, ни другого, поэтому билет не мог бы стать `verified`.
2. Сбой сборки при наличии прежнего итога не типизируется как медиа-инцидент: проверка перечитывает СТАРЫЙ файл и выдаёт `passed`, сбой
   остаётся общим `contract_rejected`. Без прежнего итога инцидент `media_failure` есть, но допуска нет (`node_not_admitted`).
3. Основа ревизии входа не записывается для попытки сборки без управляемой области (`recovery_input_revision` пуст), поэтому проверке
   ревизии нечего сравнивать; для сборки нужна ревизия всех кадров, а не только запросов платной задачи.
4. Решение модели не предлагает `retry_same` для этой ноды (проверено), аварийный стоп, один билет на запуск и бюджет надзора
   заработают для сборки только вместе с п. 1-3.
5. `audio`: вердикт `resume_local` (готовый файл на диске) есть, но у него нет исполняемой операции: файл становится результатом ноды только
   её собственным запуском (запись артефакта и таймингов кадров), а перезапуск рабочим процессом упирается в п. 1. Без POST (в
   `resume_only` ElevenLabs отказывает до отправки) это уже доказано отдельно: `tests/test_media_tranche_local.py`.
6. `sfx_gen`: вердикта `resume_local` нет вообще; готовые файлы события нода переиспользует сама по чекпоинту, повтор по событию один и
   только после ответа провайдера делает нативный слой.

Что нужно для допуска (не сделано): общий путь «повтор рабочим процессом для не-модельной ноды» с проверкой по независимым фактам
(отчёт проверки результата, файл, sha256, `approve_final` не тронут), запись основы ревизии для сборки, типизация сбоя сборки при наличии
прежнего итога, режим `resume_only` на всю попытку. Это отдельная работа в `recover_node` и `reconcile`, а не настройка ноды.

**Проверено сухими прогонами** (подменён только HTTP провайдера, настоящие: журнал, диагностика, надзор решений, защиты, билет,
независимая проверка файлов; ffmpeg создаёт настоящие файлы): `tests/observe_v1/test_media_dry_run_videos.py`, `..._items.py`,
`..._music.py` (общая основа `media_dry_run_base.py`). Сценарии каждой ноды: рестарт посреди опроса и возобновление той же задачи
без второго createTask; опрос не уложился (задача открыта): `human_review` и ноль новых запросов; неизвестный исход отправки: типизированный
отказ, ноль опросов; провалившаяся задача: отказ в платной отправке; один билет на ноду и идемпотентный повтор; аварийный стоп;
потолки расходов (ни одного резервирования и учёта траты); смена входа запроса; `user_stop`; ноды вне допуска; застрявший билет.

## Что не подключено (честно)

- Платная повторная отправка надзором (`retry_same` у `media_recovery`) не подключена: её делает нативный слой или человек. Причина
  описана выше; без отдельного допуска управляемого платного транспорта это небезопасно.
- `hero`, `audio`, `sfx_gen`, `assemble`: под наблюдением, коды причин в таблице. Для `assemble`, `audio`, `sfx_gen` допуск надзора
  проверен сухим прогоном и не выдан: что доказано и чего недостаёт, в разделе «Локальные медиа-ноды».
- Снятие блокировки неизвестного исхода человеком (`media.release_unknown`) есть; автоматически (надзором или планировщиком без
  подтверждения) её не снимает никто. Не проверено на живых провайдерах: как Kie и Outsee ведут себя при втором списании за тот же ключ.
- Живых прогонов нет. План потолков остаётся в `docs/MEDIA_NODES_READINESS.md` (раздел 6): картинка до $0.06, клип Kling до $1,
  музыка до $0.10, звуки до $0.05, озвучка до $0.10; Seedance 2.5 только по отдельному разрешению. Не доказано без живого провайдера:
  реальные ответы Kie на опрос и скачивание, сроки хранения результата, реальные клипы для `ffprobe`.
- Узлы `videos`, `items`, `music` в сухом прогоне вызывают собственное платное место ноды (лестница видео, вызов Kie с именами файлов ноды,
  у `music` настоящий `generate_music.run`); браузерная лестница Outsee и GPT-перепись предметов в прогоне не участвуют.

## Не сделано и не проверено

- Живые прогоны `sfx_plan` и `animation_prompts` (нужны деньги и подтверждение владельца). Сухие прогоны без сети есть у обоих
  (`test_sfx_plan_dry_run.py`, `test_animation_prompts_dry_run.py`); у `animation_prompts` проход идёт через настоящий исполнитель
  с лентой картинок, но настоящий ответ модели по ленте и настоящий формат пар «ID изображения / текст» не проверялись.
- `animation_prompts`: проваленная проверка результата (например, не создан `shot_02`) сама инцидента не даёт, типизирован только
  факт деградации. Повтор после применённого пакета остаётся запрещён и не доказан безопасным.
- `sd_agent`: повтор запрещён и не доказан безопасным ни для одного агента. Сухой проход по настоящему шагу сделан для
  `characters`, `world` и устаревшего `scene_design`; `skeleton` (черновик плюс редактор), `action` (кусками) и `camera` с
  ошибкой разбора через настоящий шаг не прогонялись, у них проверены только чистые проверки среза и ячеек. Контракт среза
  выведен из кода, а не из живых ответов модели; живой ответ может нарушить его так, как здесь не предусмотрено.
  Качество сцен не оценивается.
