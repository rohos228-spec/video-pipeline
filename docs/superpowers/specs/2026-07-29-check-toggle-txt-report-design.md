# Design: тумблер «Проверка» + единый TXT-отчёт

Дата: 2026-07-29  
Статус: draft → ожидает ревью пользователя  
Область: нода `excel_gpt` (Работа с GPT), отчёт проверки, forward файлов

## Проблема

1. Отчёты проверки сейчас — JSON `vp.check.v1` / свободный текст; нет единого читаемого `.txt` с полным багрепортом.
2. Роль «Проверяет» не гарантирует, что агент опирается на **исходный промт работы**; часто уезжает в свой этапный промт и пишет странные отказы.
3. Не у каждой ноды «всё со стрелок = промты для проверки» — нужен явный режим.

## Цели

- Явный тумблер **Проверка** на ноде «Работа с GPT».
- При включении: проверка **по исходному промту источника** (нода по входящей стрелке).
- Всегда писать унифицированный **`check_report.txt`**.
- Опционально чинить файл в той же ноде (второй тумблер).
- Дальше отдавать исходник или исправленный файл + отчёт.
- Стрелки Ок/Не ок читают `verdict:` из txt.

## Не цели

- Отдельный тип ноды в палитре.
- Автоподмешивание промтов на всех excel_gpt без тумблера.
- JSON-схема как основной формат отчёта для человека (JSON может остаться внутренним fallback/парсером, но deliverable — txt).

## UI

На пульте excel_gpt:

| Контрол | Значения | Дефолт |
|---------|----------|--------|
| **Проверка** | off / on | off |
| **Чинить** (видно только если Проверка=on) | fix / report_only | fix |

При `Проверка=off` поведение ноды как сейчас (свой промт, outputMode, emitKinds).

При `Проверка=on`:

- Формат ответа GPT для пользователя = txt-отчёт (не «Excel проекта» как основной выход отчёта).
- Emit по умолчанию: файл (inputs или fixed) + `reply_txt` / отчёт.

## Поведение при Проверка=on

```text
входящие стрелки
  → файлы (takeFromEdges)
  → исходные промты источников (активный master + accompanying)
       ↓
собрать check-system prompt + шаблон отчёта
       ↓
GPT: проверить файл [+ чинить если mode=fix]
       ↓
check_report.txt  (всегда)
файл: original | fixed
       ↓
emit дальше + verdict для pass/fail edges
```

### Источник промта

1. Для каждой входящей связи взять `source` node key.
2. Прочитать активный мастер-промт этой ноды (`prompt_slot_variants` / default step) + короткий текст (gpt text), если есть.
3. Несколько источников — склеить блоками с заголовком `### source: <nodeKey>`.
4. Если ни одного промта не найдено → `canRun=false`, ошибка: «нет исходного промта для проверки».

Не подмешивать произвольные промты самой check-ноды как «правила работы», кроме короткого accompanying пользователя (опционально как доп. указания ревьюера).

### Чинить vs только отчёт

- **fix**: агент может сохранить исправленный файл и указать путь в секции `forward` (`file: fixed`, `path: …`). Система кладёт файл в uploads ноды / rewrite и отдаёт дальше.
- **report_only**: файл на диске не переписываем; `forward.file: original`; в `actions` — что стоило бы сделать.

## Формат `check_report.txt`

Строго эти секции, в этом порядке. Язык: русский. Без markdown-заборов с JSON вокруг.

```text
# ОТЧЁТ ПРОВЕРКИ
verdict: pass|fail
mode: fix|report_only
source_prompts: <nodeKey[, nodeKey…]>

## summary
2–4 предложения: итог.

## analysis
Что проверяли и по каким правилам из исходных промтов; что увидели в файле.

## findings
Список ошибок и рисков:
- [error] …
- [warn] …

## related
Связь findings с источником:
- <finding-id или краткий текст> → промт:<узел> | лист:… | строка:… | поле:…

## logic
Что выглядит логично / согласовано с промтами работы.
Что выглядит странно или противоречит.

## actions
Что сделано в этой ноде.
Что осталось (человеку / следующей ноде).

## forward
file: original|fixed
path: <относительный путь от корня проекта или —>
```

### Парсинг для пайплайна

- `verdict:` → `gateStatus` pass/fail (ветки Ок/Не ок).
- `forward.file` + `path` → выбор файла для emit (fixed path если существует).
- Весь файл → `gpt_reply.txt` или отдельное имя `check_report.txt` (предпочтительно `check_report.txt` + копия/symlink логики emit `reply_txt` на этот файл).
- При битом/пустом отчёте → `verdict=fail`, `raw_error`.

Совместимость: если модель всё же вернула старый JSON `vp.check.v1`, парсер конвертирует в txt-шаблон (summary←summary, findings←checks, …) и сохраняет txt — чтобы старые промты не ломали пайплайн.

## Конфиг (meta)

`meta.excel_gpt_nodes[nodeKey]`:

```json
{
  "checkMode": false,
  "checkFix": true
}
```

- `checkMode: true` ≡ тумблер Проверка.
- `checkFix: true` ≡ Чинить; `false` ≡ Только отчёт.

При `checkMode` UI/resolve показывают `checkMode`, `checkFix`, список `sourcePrompts` (какие ноды/пути промтов подтянутся).

## Затронутые места (ориентир реализации)

- `web/.../gpt-operator-menu.tsx`, `excel-gpt-settings-panel.tsx` — тумблеры.
- `app/services/gpt_operator.py` — config/normalize/resolve/emit для check report.
- `app/orchestrator/steps/enrich_xlsx.py` / `gpt_operator_client.py` — сбор промтов источников, прогон, запись `check_report.txt`.
- Новый модуль или расширение `check_analysis.py` — parse/write txt report; footer с шаблоном txt (не JSON-first).
- Тесты: parse txt, assemble prompts from edges, fix vs report_only, verdict edges.

## Критерии приёмки

1. При выкл «Проверка» — регрессий нет.
2. При вкл — в resolve видны source prompts со стрелок; без них run блокируется понятной ошибкой.
3. После run всегда есть `check_report.txt` с секциями summary…forward.
4. «Только отчёт» не меняет входной xlsx; «Чинить» при успешной правке отдаёт новый файл.
5. Emit отдаёт файл + отчёт; pass/fail стрелки следуют `verdict:`.
6. Список файлов/хранилище по-прежнему могут принять отчёт как txt.

## Открытые мелочи (дефолты, если не скажешь иначе)

- Имя файла отчёта: `check_report.txt` в `excel_gpt_uploads/<nodeKey>/`.
- Несколько входящих источников: все промты + все файлы (как сейчас multi-edge).
- Старый `vp.check.v1` — только fallback конвертер в txt.
