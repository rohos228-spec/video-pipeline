# Предложение: ядро + пакеты нод вместо двух веток

## Проблема
- Есть основная версия (`main`, веб) и `housepc`, где разработчик делает новые ноды.
- Эти ветки постоянно конфликтуют. Сделан контейнер для `housepc`, в вебе можно выбрать один из двух вариантов, но при каждом обновлении приходится сливать обе ветки.
- Планируется «любое количество нод», которые люди будут добавлять сами. При нынешнем устройстве каждая новая нода — это правки в десятках общих файлов, то есть новый источник конфликтов.

## Что показал разбор кода
- Добавить один новый тип ноды в `main` сегодня значит править примерно 25–30 файлов backend и 15–20 файлов frontend. Тип ноды прописан вручную в десятках таблиц (`pipeline.py`, `auto_advance.py`, `reset_step.py`, `quote.py` и др.). Палитра студии статична.
- Ноды из `housepc` — это не новые типы в реестре, а ноды `excel_gpt` с суффиксами `_fw_*`, у которых логика зашита в условия внутри `enrich_xlsx.py`. Конфликтуют не реестры, а исполнители. Пробное трёхстороннее слияние: 83 файла с правками с обеих сторон, 57 с конфликтами, 233 фрагмента.
- «Контейнер» — это деплой двух веток разными сервисами. Он не уменьшает объём слияния, он только позволяет запускать оба варианта.

## Предложение
Ядро (`main`) не знает про конкретные ноды. Нода — это папка-пакет с манифестом (`node.yaml` / `node.json`): тип, название, порты, промпт, настройки по умолчанию, версия интерфейса, способности для оркестратора. Реестр находит пакеты при старте, каталог и палитра строятся из реестра. Нода, которой достаточно «промпт + контракт», добавляется без единой строки кода. Экзотическим нодам нужен пакет с кодом (следующая версия интерфейса).

## Что уже доказано на прототипе (локально, ничего не отправлено)
Ветка `poc-node-packages` на копии `WebVideoPipeline/main`, коммит `8146288`.
- Новая нода добавляется папкой: в тесте вторая папка с манифестом появляется в каталоге и реестре, список встроенных нод не меняется, **ни один файл ядра не правится**.
- Некорректный пакет (нет названия, неверный id, неизвестный порт, промпт за пределами папки, id совпадает со встроенным, битый YAML, несовместимая версия) пропускается с понятной ошибкой в каталоге и не роняет запуск.
- Запуск идёт через уже существующий канал `excel_gpt`: без новых статусов проекта и без миграций БД. Промпт из манифеста доходит до исполнителя; явный выбор промпта пользователем в Node Studio приоритетнее.
- Тесты: 19 новых + 5 существующих по каталогу = 24 прошли. В 25 целевых файлах и в расширенном наборе из 73 файлов до и после изменений одинаковые результаты (223 прошли / 2 упали и 615 прошли / 22 упали / 2 ошибки; падения те же самые и без изменений).
- **Единоразовая правка ядра:** 7 файлов, 42 строки добавлено, 7 удалено. Новый код: загрузчик и манифест около 550 строк, тесты 431. **На каждую новую ноду правок ядра: 0.**

## Чего прототип не делает (честно)
- Выполняются только ноды вида «LLM по промпту» (`kind: llm`). Ноды с кодом отклоняются; исполнитель, верификатор, хранилище и профиль модели в манифесте пока не реализованы.
- Интерфейс (палитра) не менялся: нужны 4–5 файлов и около 80–100 строк. Важный нюанс: сериализация узла на фронтенде отбрасывает неизвестные поля, и пакетная нода без правки превратится в обычную.
- Нода-пакет сейчас идёт через статусы «enrich 1», одна нода на проект за раз; цепочки нескольких пакетных нод не проверялись.
- Ошибка в существующем коде не тронута: для обычных overflow-нод слот 0 даёт `KeyError`.
- Образцы пакетов лежат в корне по умолчанию и попадают в палитру везде, нужен флаг или другой каталог.
- Не реализованы группы пакетов (например, `script_frames_qc` как шесть нод-пакетов), хуки миграции графов, общие тесты соответствия для любого пакета.

## План внедрения по шагам
1. Принять интерфейс пакета (`node.yaml`, версия API) как контракт между ядром и нодами.
2. Внедрить загрузчик в `main` (единоразовая правка ядра, как в прототипе) и исправить палитру/сериализацию на фронтенде.
3. Вынести из `housepc` одну группу (`script_frames_qc`) в пакеты нод; убедиться, что исполнитель выбирается по манифесту, а не по условиям в `enrich_xlsx.py`.
4. Перенести остальные ноды `housepc` по одной. После этого `housepc` перестаёт быть вариантом продукта: остаётся короткая ветка для экспериментов с регулярным слиянием в `main`.
5. Убрать контейнер-выбор «из двух» и отдельный деплой второй ветки.
6. Добавить тесты соответствия: любой пакет обязан пройти (контракт, журнал, способности) до загрузки.
7. Подключить оркестратор: способности ноды берутся из манифеста, а не из условий по типу.
