# Безопасные умолчания (фаза B)

Все умолчания сохраняют текущую локальную работу владельца. Настройки читаются из `.env` / окружения.

## Доступ к изменяющим ручкам (B1)
- Веб-авторизация включена (`WEB_AUTH_USER` + `WEB_AUTH_PASSWORD`): ничего не меняется, работает `AuthDep`.
- Веб-авторизация выключена (умолчание): POST/DELETE надзорного слоя (`/api/projects/{id}/observations/*`: запуск, kill switch, решения, профили, действия, сброс неопределённости коммита, pin) и слоя действий (`/api/action-layer/*`: preview, from-text, from-macro, макросы, approve, run, stop) принимаются **только с loopback** (127.0.0.1, ::1). Остальным клиентам: `403 {"code": "local_only"}`.
- `ORCHESTRATOR_ALLOW_REMOTE_WITHOUT_AUTH=true` снимает это ограничение (не рекомендуется без авторизации).
- Чтение журнала (`GET .../observations/*`, включая stream/telemetry/kill-switch) требует вход, когда авторизация включена.
- Реализация: одна зависимость `app/services/access_guard.py` (`LocalOnlyDep`).
- CORS остаётся `*`. При старте с выключенной авторизацией и `WEB_HOST`, не равным loopback, в лог пишется предупреждение `SECURITY: ...`. Умолчание `WEB_HOST=127.0.0.1`.

## Редакция и облачный трекер (B2)
- `error_message`, `project_source`, `metadata` перед записью в трекер (локальный SQLite и облако) проходят через `redact` (`api_tracker_hook.record_api_call`, `observation._track_api_cost`). Тексты исключений в журнале решений (`escalate`, отказ повтора) и SSE-ошибка также редактируются.
- `API_TRACKER_CLOUD_ENABLED` (умолчание `true`): `false` отключает отправку строк вызовов в облако; локальная запись остаётся, строка помечается `synced=1`, чтобы фоновая досылка её не отправила. Переключение аварийного рубильника (`toggle_killswitch`) и чтение его облачного состояния флагом не затрагиваются.

## Чат-оркестратор (B3)
- Каждое выполненное, отказанное и подтверждённое действие чата (`/db/projects/{id}/orchestrator/chat`, `confirm-git-push`, `confirm-delete-projects`) пишется в append-only журнал `action_layer_history` с событием `chat_action`: кто (`web_operator:<хеш токена>` или `local_web_operator`, плюс адрес клиента), когда, имя действия, исход (`ok`, `error`, `refused`, `pending_confirm`), `params_digest` (sha256 от аргументов после редакции, значений нет).
- `CHAT_CODE_ACTIONS_ENABLED` (умолчание `false`): по умолчанию чат отказывает в `edit_files` и `git_commit_push` (и в `confirm-git-push`, ответ `403`) с сообщением «Правка кода и git push из чата отключены… задайте CHAT_CODE_ACTIONS_ENABLED=true»; отказ пишется в журнал как `refused`. Остальные действия (запуск шагов, параметры, `read_file`, `run_tests`) работают. В режиме «Фикс багов» модели сообщается, что правка кода отключена, и она объясняет причину словами. `true` возвращает прежнее поведение: правка `app/`, `tests/`, `prompts/`, коммит и push (push по-прежнему требует подтверждения кнопкой).

## Остаточные риски
- Аварийный рубильник (kill switch) до шага A07 плана `docs/REGISTRAR_FULL_PLAN.md` НЕ охватывал ручные платные кнопки и часть нативных платных швов (прямые вызовы провайдеров вне слоя действий и оркестратора). Не полагайтесь на него как на полную защиту денег; статус после A07 см. в плане и отчёте интегратора, живой проверки нет.
- Проверка loopback опирается на адрес сокета; обратный прокси на той же машине делает все запросы «локальными».
- Страницы в браузере оператора по-прежнему могут слать запросы на localhost (CORS `*`) — защита от этого только через включённую авторизацию.
- Чат с явно включённым `CHAT_CODE_ACTIONS_ENABLED=true` может править `app/`, `tests/`, `prompts/` и делать push.

## Версионные миграции таблиц оркестратора
- `app/services/schema_migrations.py`: в каждой базе таблица `schema_migrations` (id, applied_at, checksum). Миграции идут по порядку id (`0001_observation_core` … `0010_change_proposals_reject_columns`, всего 10), каждая в своей точке сохранения вместе с записью о применении: сбой откатывает только её (частичной схемы и записи нет), останавливает запуск и сообщается (`MigrationFailed` и строка `ERROR` в логе), уже применённые остаются.
- Миграции идемпотентны: база, созданная до появления раннера, просто получает записи без изменения данных и таблиц; повторный запуск ничего не меняет. Контрольная сумма — отпечаток таблиц и триггеров миграции; расхождение (модель изменилась без новой миграции) пишется предупреждением `drift` и не перезаписывается. Для изменения схемы добавляется новая миграция в конец списка `MIGRATIONS`.
- Стартовый путь (`app/main.py`, `app/web/api.py`) вызывает `migrate_orchestrator_schema`; проектные базы (`project.db`) получают `0001`, `0007` и `0008`. Миграция `0010` добавляет столбцы отклонения в `change_proposals` (раньше ручной ALTER). Миграции `0007`-`0009` добавляют колонки к старым таблицам `frames`, `frames_space`, `projects` тем же DDL, что раньше выполнялся ALTER при старте (результат схемы не изменился, сбой откатывает миграцию целиком); `migrate_db_v2_schema` и `migrate_scene_space_schema` остались тонкими обёртками для старых вызовов. Остальные таблицы вне оркестратора раннер не трогает; отдельная база трекера API (`api_calls`) по-прежнему обновляется своим кодом.

## Вход по паролю (решение владельца, 2026-10-06)

Пока всё работает локально на одном компьютере, вход по паролю не включён. Изменяющие запросы оркестратора (запуск платных нод, одобрение планов, правки промптов) принимаются только с loopback-адреса. Когда веб-версию выложат на сервер или ею начнут пользоваться несколько человек, вход нужно включить до открытия доступа извне. Без него любой, кто знает адрес, сможет нажимать кнопки и тратить деньги, и нельзя будет видеть, кто что одобрил.
