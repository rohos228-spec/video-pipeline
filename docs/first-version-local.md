# Локальный кандидат: текстовый оркестратор v1

Поддерживаемая область — шесть нод группы `script_frames_qc`, обязательный JSON,
payload и разрешённый QC no-op. Наблюдение, rule-based diagnosis, Decision,
Actions, профиль конкретной попытки и runtime verification дополняют исходный
worker. Media, публикация, произвольный код, произвольный prompt и другие
провайдеры не входят в эту версию.

## Обычный интерфейс

1. В уже установленной среде с зависимостями запустить `STUDIO.cmd`, пункт 1,
   либо `scripts/run-backend.ps1`. На Linux — `python -m app.main` из корня.
   Это исходные запускатели; install/update команды не нужны для этого кандидата.
   Открыть `http://127.0.0.1:8765`, выбрать **тестовый** проект и панель оркестратора.
2. В секции «Наблюдение» выбрать группу и включить наблюдение. Сохранённый
   execution восстанавливается из истории; его scope отображается отдельно.
   При расхождении с текущими группами UI не подставляет первую попавшуюся группу.
3. «Диагностика» показывает факты, гипотезы, полноту и отставание. Unknown и
   not_checked не означают успех. Полные очищенные тела лежат локально в
   `DATA_DIR/observations/bodies`; журнал и история содержат ссылки и хеши.
4. Управление включается отдельно: обоснование, выбранная группа, общий лимит
   запросов. После разрешения scope/graph/лимит закреплены. Кнопка запуска
   отправляет одну pending-ноду через штатный API, дальнейший путь ведёт runtime.
5. Для Decision указать **локальный** JSON политики в `ORCHESTRATOR_RUNTIME_CONFIG`.
   Исходный `config/orchestrator-runtime.example.json` выключен, allowlist пуст.
   Модель, reasoning, выходные токены, точный маршрут и инструменты задаются в этом
   файле, ключи туда не помещаются. Уже установленный штатный клиент получает
   секрет через существующую конфигурацию отдельно. Наличие ключа не даёт permission.
   При разрешённом сценарии оператор отдельно включает «Цикл решений» в панели.
6. Профиль — только одобренный catalog entry и конкретная нода/attempt. В панели
   видны base/candidate, одобрение и результат. Production `profiles={}` по умолчанию.
   Смена файла во время execution блокируется; для другой политики нужен новый
   явно согласованный execution. Не менять JSON ради обхода текущего отказа.

### Три разных остановки

| Действие | Результат |
| --- | --- |
| Остановить наблюдение | Прекращает наблюдение; не отменяет обычную задачу. Managed-путь без обязательного audit не получает новых отправок. |
| Приостановить управление | Hold execution: новые управляемые запуски/отправки запрещены. Уже отправленный HTTP-запрос этим не отменяется. |
| Остановить над графом | Штатная остановка задачи проекта / user_stop. Supervisor её не снимает. |
| Выключить цикл решений | Отключает новые решения модели; существующий action не становится отменённым. |
| Закрыть execution | Отзывает разрешение после завершения активных работ; не означает done всего WorkflowRun. |

История действий, proposal, policy refusal, worker_result, verification и
human_review находятся в той же панели. При ошибке чтения controls UI блокирует
изменяющие кнопки до подтверждённого ответа сервера. Неверный prompt или модель
не исправляются автоматически произвольным редактированием файлов.

## Безопасная бесплатная проверка комплекта

Используется существующий Docker runner и уже подготовленный локальный image
`vp-offline-diagnostic:20260924`. Все контейнеры приложения `--network none`,
ответы выдаёт loopback fixture, ключ синтетический. Внешних зависимостей не ставить.
Архивный exhausted seed передаётся **явным** `-DenialSeed`; он не часть приложения
и не хранится в Git. Fixture-функции теперь находятся в
`tests/observe_v1/group_runner.py`, скрытого импорта `../diag_v2` для group нет.

```powershell
.\scripts\test_observe_offline.ps1 -Target group -GroupMode decision-managed-pilot `
  -DenialSeed 'ПУТЬ-К-СОХРАНЁННОМУ-SYNTHETIC-exhausted-checkpoint' `
  -ResultsRoot 'НОВАЯ-ПАПКА-РЕЗУЛЬТАТОВ'
```

Вариант `decision-managed-review` проверяет добровольную передачу человеку без
recovery. Оба режима используют исходный `app.main`, API, Observer/Decision,
Actions, worker и БД. Фикстуры задают только внешние ответы. Это не проверка
качества реальной модели. `-Browser` оставляет живой API/UI на короткое время
для приёмки через существующий локальный browser bridge. Это тестовая команда,
не способ включения production. Архивы, ключи, ответы моделей и БД не коммитить.

## Подготовленный следующий managed-пилот — online запрещён

Шаблон: `config/managed-text-pilot.example.json`. При бесплатной проверке в копии
создаются `prepared-managed-pilot.json` и `synthetic-managed-runtime.json`.
Execution UUID сохраняет связи seed; отдельные run_id, DATA_DIR и экземпляр БД
отделяют запуск. Существующие 9 native attempts / 18 reservations не сбрасываются
и не воспроизводятся платно. Цель — текущий incident
`n_excel_gpt_fw_script`, а не старый QC-срез с неизвестным retry.

Старый seed `actions-v1-final/recovery-a-08` отвергнут текущей защитой ревизий:
после него изменились `enrich_xlsx.py` и `node_write_contract.py`. Его история
не переписана. Для актуальной бесплатной проверки прежний `recovery-a` runner
повторно получил exhaustion на синтетических ответах с текущим кодом и штатным
backoff. Сохранённый им checkpoint имеет свои настоящие 9 attempts / 18
reservations и новый execution UUID; это **новое синтетическое происхождение**,
не продолжение старого execution. Последующие копии сохраняют именно его 18.
Пути и результаты указаны в отчёте локального кандидата.

Один incident/source attempt закрепляется в `incident_scope` runtime binding.
Разрешена одна recovery этой ноды; другая нода/incident/attempt, изменённый graph,
input/config, user_stop, uncertain и audit failure блокируют действие. Смена
runtime-конфига проверяется общим счётчиком до отправки worker/Decision.
Профили в первом пилоте выключены. Allowlist:
`read_events`, `read_contract`, `retry_same`, `wait`, `human_review`, `finish`.
Модель вправе выбрать человека; фиксированный успешный retry не требуется.

| Возможные реальные обращения | Основание |
| --- | --- |
| Decision: до 3 POST | Существующий MAX_STEPS, включая исправление decision JSON |
| Целевая recovery: 1 POST + возможный 1 JSON retry | Одна новая attempt после сохранённого exhaustion |
| Продолжение группы: 4 исходных POST | Проверка сценария, действие сцены, кадры, QC; HTML локален |
| Дополнительные JSON retry: до 3 слотов | Для action/shots/QC; сценарий проверки возвращает текстовый verdict |
| Verification: 0 самостоятельных модельных POST | Существующая детерминированная сверка журнала, БД и attempt |

Итого номинальный успешный путь с тремя Decision turns: **8 новых POST**.
Подготовленный общий allowance: **12 новых запросов**, total managed limit **30**
с учётом старых 18. Он получен как 3 Decision + 5 worker + 4 JSON retry slots,
а не является денежным потолком или обещанием пройти все ветки runtime.
Если downstream попадает в дополнительные native attempts/split, они расходуют
тот же allowance и могут остановиться раньше исчерпания всех native retries.
Все шесть нод группы — согласованная граница; `n_script` и media запрещены.
Worker prompt/model/data не меняются ради результата. Настройки исходного seed,
включая транспортные retry, сохраняются; дополнительные отправки также расходуют
общий лимит. Отключение retry меняет settings revision и не является незаметной
правкой перед восстановлением.

До настоящего запуска нужны отдельное разрешение на изменяющий managed-сценарий
и его расходы, новая копия/ledger, fresh keyless preflight, сверка фактических
worker token settings и маршрута. Текущий online launcher остаётся **read-only**:
его entrypoint запрещает business writes и не запускает worker. Подготовленный
managed режим проверяется существующим offline group runner; read-only команду
`-OnlineAuthorized` нельзя использовать для его активации. Связку с уже имеющимся
шлюзом потребуется явно активировать в существующем launcher после согласования;
новый шлюз/адаптер не требуется. Цена и денежная верхняя граница не подтверждены.

## Среда и ограничения

Сборка и проверки выполнены в существующих Linux Docker images на Docker Desktop;
Windows использован как host PowerShell-запускателя. Это не приёмка всех native
Windows режимов, GPU, медиа или установки заказчика. В текущем worktree нативный
backend с настоящим `.env` не запускался. Готовый `web/out` включён в feature-ветку.
Миграции Observe/Actions/Decision/Profiles аддитивные и выполняются исходным
startup; на рабочих БД в этой приёмке не применялись.

Реальный read-only сценарий принят отдельно: два ответа, read_contract,
human_review, settled ledger. Это не разрешение реальной recovery и не доказательство
независимого установления причины. Известный нюанс того запуска: HTTP gateway
graceful, ledger settled, служебный контейнер exit 137 — три разных результата.
