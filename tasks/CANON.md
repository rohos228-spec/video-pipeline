## 2. Доменные правила

### 2.1 Крупности

Коды: `EWS`, `WS`, `FS`, `MWS`, `MS`, `MCU`, `CU`, `ECU`.
Соответствие русским значениям в Базе: дальний → EWS, общий → WS, в полный рост → FS, второй средний (по колени) → MWS, первый средний (по пояс) → MS, крупный (голова и плечи) → MCU, крупный (лицо) → CU, деталь → ECU.

Правило стыка соседних кадров одного объекта:

| Стык | Оценка |
|---|---|
| одинаковая крупность | ошибка |
| соседняя крупность | предупреждение, допустимо только при смене угла ≥ 30° |
| через план (CU↔MWS, MS↔WS, MCU↔FS) | норма |
| CU→ECU | разрешённое исключение |
| EWS→WS | разрешённое исключение |
| разрыв через два и более шага | предупреждение, допустимо только как осознанный smash |

Лестница (индекс 0..7): `EWS WS FS MWS MS MCU CU ECU`.
«Через план» = разница индексов 2. «Через два и более» = разница ≥ 3, кроме двух исключений выше.
«Осознанный smash»: `beat_role=insert` или `crossing_method` не NULL не делают smash сами; smash помечается `beat_role=insert` **и** разрывом ≥ 3. Без этой пометки — warning.

Легаси-коды камеры (`VLS`,`LS`,`Insert` и т.д.) в `frames_space` не хранить. Маппинг при чтении attrs: VLS→EWS, LS→WS, Insert→ECU. Неизвестный код — error валидатора, не тихий пропуск.

### 2.2 Правило 30 градусов

Между соседними кадрами одного объекта точка съёмки меняется минимум на 30°. Меньше — ошибка «скачок». Если координат камеры нет, угол считается по смене ракурса из перечня 2.4.

Горизонталь порядок для угла-замены (шаг = 45° номинал, сравнение соседних имён): `frontal`, `three-quarter`, `profile`, `rear three-quarter`, `over-the-shoulder`, `from behind`. Соседние имена < 30° эквивалента, если не сменилась вертикаль на два+ шага. Вертикаль порядок: `eye-level`, `slight low`, `low`, `slight high`, `high`, `overhead`, `dutch`. Если нет координат: ошибка «скачок», когда и `angle_h` совпал, и `angle_v` совпал.

### 2.3 Ось действия и сторона

Ось — линия между двумя субъектами взаимодействия. Если субъект один, ось идёт от него к объекту его внимания.

Сторона считается косым произведением:

```
axis   = b - a
to_cam = camera - a
cross  = axis.x * to_cam.y - axis.y * to_cam.x
cross > 0 → сторона A ; cross < 0 → сторона B ; cross == 0 → вырожденный случай, отклонять
```

Порядок пары нормализуй (сортировка id), иначе `[a,b]` и `[b,a]` дадут противоположные стороны на одинаковой геометрии. Первый кадр сцены выбирает сторону, дальше она заперта для этой пары. Все последующие кадры этой пары ставятся только с запертой стороны.

При трёх и более персонажах осей столько, сколько пар взаимодействия; в каждый момент действует ось активной пары кадра.

`axis_pair` в БД — канон `"id1|id2"` после сортировки id как строк. Камера в `plan` имеет id `"cam"`.

### 2.4 Ракурсы

Вертикаль: `eye-level`, `slight low`, `low`, `slight high`, `high`, `overhead`, `dutch`.
Горизонталь: `frontal`, `three-quarter`, `profile`, `rear three-quarter`, `over-the-shoulder`, `from behind`.

### 2.5 Положение и направление на экране

`screen_pos` — следствие стороны, а не решение: при камере на стороне A и оси a→b субъект `a` оказывается в одной половине кадра, `b` в другой, и это должно совпадать с расчётом. Расхождение — ошибка.

Формат `screen_pos` JSON-строка: `{"<id>":"L"|"R"|"C",...}` для участников оси. Правило: при `cross>0` (сторона A) субъект `a` (первый id пары до нормализации оси внимания, но ключи — реальные id) — см. CONTRACTS: после нормализации пары `[lo,hi]`, ось = hi-lo в координатах; экран: субъект с меньшей экранной x слева. Расчёт: вектор оси повёрнутый на 90° в сторону камеры даёт «экранный право». Конкретно:

```
axis = b - a   # a,b в нормализованном порядке lo,hi где a=lo, b=hi
right = (axis.y, -axis.x)   # поворот по часовой в плоскости x/y
# сторона A (cross>0): камера слева от оси a→b в этой системе
# экран: проекция позиции на right; меньшая проекция → L
```

`screen_dir` — направление движения субъекта по экрану: `L→R`, `R→L`, `to camera`, `from camera`, `none`. Держится постоянным всю сцену.

Если движется несколько субъектов, канонический `screen_dir` кадра — у субъекта активной оси с ненулевой дельтой; иначе `none`.

### 2.6 Правила поворотов и переходов

Легально сменить сторону оси можно только явно названным способом, и он обязан быть записан в поле кадра:

| Способ | Что должно быть в кадре | `crossing_method` |
|---|---|---|
| POV-мост | кадр от лица субъекта, затем новая сторона | `pov` |
| переустановочный общий | общий план, заново показывающий географию | `reestablish` |
| отвесный кадр сверху | overhead, обнуляющий ось | `overhead` |
| проезд камеры через линию | движение камеры, пересекающее ось внутри кадра | `camera_move` |

Молчаливый перескок на другую сторону — ошибка.

Сменить направление движения по экрану можно только промежуточным кадром, где субъект физически поворачивает внутри кадра. Разворот без такого кадра — ошибка. Помечать поворот: `beat_role=insert` и в `space_delta_json` поле `"turn": true` у субъекта, либо `crossing_method` не для стороны, а отдельный факт: `space_delta_json.turn_subject`.

### 2.7 Переустановка

`reestablish_due` поднимается, когда: субъект заметно переместился, кто-то вошёл или вышел, изменился состав пары взаимодействия, либо подряд прошло три и более кадра крупнее MS (индекс > MS). Пока флаг поднят, следующий кадр обязан быть WS или EWS. После него флаг гасится.

«Заметно переместился»: евклидова длина дельты xy ≥ 1.0 м.

`reestablish_due` хранится на кадре, который **породил** долг; долг должен быть погашен **следующим** кадром (WS/EWS). Валидатор смотрит кадр k с due=1 → кадр k+1 shot_size in {WS,EWS}.

### 2.8 Драматургия сцены

Сцена обязана поворачивать: ценность, заряженная в начале плюсом, к концу заряжена минусом, или наоборот. Заряд не изменился — сцена не событие, а экспозиция; помечать как ошибка уровня warning с текстом «сцена не поворачивает».

Заряд в `scenes_space.space_json.value_charge`: `{"start":"+","end":"-"}`.

Сцена разбивается на биты — обмены действие/реакция. Один бит помечается точкой поворота. Точка поворота обязана иметь собственный кадр (`beat_role=turning_point`).

### 2.9 Критерии «сцена интересная»

| Критерий | Порог |
|---|---|
| разнообразие крупностей | минимум 3 разных кода на сцену |
| уникальность акцентов | ни один `accent` не повторяется внутри сцены |
| точка поворота покрыта | есть кадр с ролью turning point |
| есть реакция или деталь | минимум один кадр класса реакция/вставка (`reaction` или `insert`) |
| нет монотонии | нет трёх подряд кадров с одинаковой тройкой «число тел + доминирующая поверхность + класс действия» |
| география держится | после каждого перемещения есть переустановка |
| покрытие достаточно | диалог двоих: минимум мастер + по одному одиночному на каждого + одна реакция |

Тройка монотонии в `space_delta_json.monotony` или выводится: `bodies` = число id в plan кроме cam/obstacles; `surface` = `plan` dominant surface string в space_json или `"ground"`; `action_class` = `beat_role` сжатый в {action, reaction, insert, establish}.

Мастер диалога: `shot_size` in {EWS,WS,FS} и оба субъекта в кадре (`screen_pos` содержит оба id). Одиночный: один субъект пары в `screen_pos` (или только он L/R, второго нет).

## 3. Модель данных

Таблицы `scenes_space` и `frames_space` — SQL из ТЗ. Доп. колонка (раздел 5 ТЗ, иначе нельзя сохранить ручные правки):

```sql
ALTER TABLE frames_space ADD COLUMN manual INTEGER NOT NULL DEFAULT 0 CHECK (manual IN (0,1));
```

Правила записи: в `plan` попадает объект только если он участник оси, объект внимания или перекрывает камеру. Остальное — в текстовое описание фона, в геометрию не лезет. Состояние на кадре = `space_json` плюс все дельты по возрастанию `shot_order`. Полные копии состояния на кадр не хранить.

Единицы: метры, `x` вправо, `y` в глубину, `facing` в градусах, 0 — в глубину (+Y), отсчёт по часовой. 90 — вправо (+X), 270 — влево (−X), 180 — на камеру из глубины (−Y). 0 и 360 эквивалентны.

Камера в `plan`: `{"id":"cam","x":...,"y":...,"facing":...}`. Obstacles: `{"id","x","y","w","h"}`.

## 4. Отображение

1. План сцены сверху. Команда генерирует SVG или PNG на каждый кадр: субъекты с направлением взгляда, препятствия, линия оси, залитая запертая сторона, маркер камеры, стрелка направления движения. На картинке подписаны `shot_order`, крупность, сторона.
2. Монтажная раскладка. Один HTML на сцену: кадры по порядку, у каждого крупность, ракурс, сторона, `screen_pos`, `screen_dir`, `accent`, роль бита. Нарушения подсвечены с текстом правила, которое нарушено. Сверху сводка по критериям из 2.9.
3. Обе команды детерминированы и запускаются одной строкой из терминала. Пути — `tasks/INVENTORY.md`.

## 5. Механизмы правки

1. Перезапись смысла сцены. Меняешь смысл сцены — пересобираются биты и разбивка на кадры, но ручные правки конкретных кадров не затираются: `manual=1` сохраняет поля `frames_space` этого uuid. Операция идемпотентна: повторный запуск на неизменённом входе не меняет БД.
2. Разбивка на кадры. Из битов сцены генерируется последовательность кадров с ролями, крупностями и сторонами, сразу проходящая правила раздела 2. Если правило не удаётся соблюсти — не подгонять данные, а добавить нужный служебный кадр (переустановку, промежуточный поворот, POV-мост).
3. Обе операции пишут в БД через слой `app.services.scene_space.store` (тот же `session_scope`, что пайплайн). Логируют diff: inserted/updated/skipped uuid.

Идемпотентность: ключ `space_json.input_hash` = sha256 канонического JSON (meaning, bits, non-manual desired shots). Повтор с тем же хешем → 0 UPDATE/INSERT.

Служебные кадры, которых не было в `frames`: создаются как Frame через существующий `db_v2.insert_frame_after` + `new_frame_uuid`, не через сырой SQL. Не затирать voiceover/промты соседей.

## 6. Валидатор

Одна команда, один прогон, ненулевой код выхода при ошибках (хотя бы один level=error). Отчёт `tasks/VALIDATION.md`. Проверки:

| Проверка | Уровень |
|---|---|
| сторона кадра совпадает с запертой стороной пары | error |
| смена стороны без записанного `crossing_method` | error |
| `screen_pos` совпадает с расчётом по стороне | error |
| `screen_dir` не переворачивается без промежуточного кадра поворота | error |
| шаг крупности по таблице 2.1 | error на одинаковой, warning на соседней |
| смена точки ≥ 30° | error |
| `reestablish_due` погашен кадром WS или EWS | error |
| вырожденный случай `cross == 0` | error |
| порядок пары нормализован | error |
| все `frame_uuid` существуют в БД, имена полей совпадают со схемой | error |
| лимиты символов промтов не превышены | error |
| в позитивной части промта нет запрещённых слов | error |
| в промте присутствуют стилевые блоки и негатив | error |
| критерии интересности 2.9 | warning |
| сцена не поворачивает | warning |

Код выхода: 2 если есть error, 1 если только warning, 0 если чисто.

## 7. Тесты системы координат

Property-based, каждый на случайных данных, минимум 200 прогонов. Без пакета hypothesis: `random.Random(seed)` циклом 200. Тест упал — сначала код, не тест.

1. Поворот и перенос всего плана целиком не меняет сторону оси ни для одного кадра.
2. Зеркальное отражение плана переворачивает сторону у всех кадров.
3. Масштабирование плана не меняет ни сторону, ни `screen_pos`.
4. Перемещение субъекта через ось переворачивает `screen_pos` и поднимает `reestablish_due`.
5. Накопление дельт по `shot_order` даёт то же состояние, что прямой пересчёт с нуля.
6. Пара `[a,b]` и `[b,a]` после нормализации дают одну и ту же сторону.
7. Камера строго на линии отклоняется с внятной ошибкой, а не молча.
8. `facing` 0 и 360 эквивалентны, 90 смотрит вправо, 270 влево.
9. Удаление кадра из середины сцены не ломает состояние последующих.
10. Идемпотентность: двойной прогон разбивки на кадры не меняет БД.
